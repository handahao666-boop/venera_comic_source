# Venera 漫画源开发日志（统一合并版 v3）

> **案例源**：漫网/香蕉漫画（`manhuau.com`、`manwang.net`）、爱看漫（`ikmmh`）、MOJOIN（`mojoin.com`）及腾讯动漫（正版，`m.ac.qq.com`）  
> **案例版本**：漫网 v1.2.0；爱看漫 v1.1.2；MOJOIN v1.0.5；腾讯动漫与其他历史案例按原记录保留  
> **文档性质**：开发记录、可复用工作流、验证规范、安全边界与维护基线  
> **编写原则**：所有站点结论必须来自实际网页、接口、页面脚本或官方文档；没有证据时必须标记为“待验证”，而不是进行推测。

---

## 1. 文档目标与最终交付标准

Venera 漫画源并不是“能打开首页”就算完成，而是一个由网页取证、数据解析、图片获取、客户端接口适配和回归验证共同构成的可维护模块。官方约定漫画源以 JavaScript 类继承 `ComicSource` 实现，核心字段包括 `name`、`key`、`version`、`minAppVersion` 和 `url`；页面能力则通过 `explore`、`category`、`search` 与 `comic` 对象提供。[1]

本日志把开发过程拆分为可审计的步骤。每一步都必须留下输入证据、实现决策、输出结果和验证结论。开发完成的最低标准，是首页推荐、搜索、分类、漫画详情、章节列表和图片加载六条链路均有真实样本验证；任何未验证项目不得写成“已支持”。

> **重点：验证优先于编写，验证也优先于发布。** 选择器、路由、分页、加密算法、密钥来源和图片响应处理都必须先经真实样本证明，再进入脚本。只通过语法检查、只看到网页能打开，或只得到空数组，均不构成“功能可用”的验证。

| 交付物 | 必须包含的内容 | 不合格示例 |
|---|---|---|
| 漫画源脚本 | 唯一 Key、标准 Venera 返回类型、真实站点解析逻辑、版本日志 | 直接复制其他源的选择器、参数或解密流程 |
| 开发日志 | 路由、HTML/JSON 字段、图片来源、错误与修复、验证结果 | 仅写“已修复”而没有样本和数据 |
| 验证脚本或步骤 | 可重复执行的输入样本、断言、预期输出 | 手工浏览一次后口头确认 |
| 发布说明 | 版本、改动范围、已验证与未验证项目 | 不区分已证实和猜测功能 |

## 2. Venera 漫画源的基础接口与数据契约

Venera 提供 `Network`、`HtmlDocument`、`Convert`、`Comic`、`ComicDetails` 等 JavaScript API。网络请求通过 `Network.get`、`Network.post` 等方法完成，HTML 通过 `new HtmlDocument(html)` 及 CSS 选择器解析；漫画列表与详情应分别返回 `new Comic({...})` 和 `new ComicDetails({...})`，而不是依赖未经验证的普通对象。[2]

| 模块 | 输入 | 合规输出 | 典型错误 |
|---|---|---|---|
| `explore.load` | 首页请求结果 | `singlePageWithMultiPart` 时返回 `{ "区块名": Comic[] }` | 返回数组或把不同页面的选择器混用 |
| `categoryComics.load` | 分类名、参数、筛选项、页码 | `{ comics: Comic[], maxPage: number }` | 猜测分类 URL、固定返回不存在的页数 |
| `search.load` | 关键词、筛选项、页码 | `{ comics: Comic[], maxPage: number }` | 将首页卡片选择器用于搜索页 |
| `comic.loadInfo` | 漫画 ID | `new ComicDetails({ title, cover, chapters, ... })` | 章节 key 与阅读 URL 不匹配 |
| `comic.loadEp` | 漫画 ID、章节 ID | `{ images: string[] }` 或符合 API 的图片加载配置 | 抓到广告占位图、未处理相对路径或加密二进制 |

`key` 是源的内部唯一标识，应使用稳定的英文、数字和下划线组合。例如本案例使用 `manhuauo_banana_v2`。显示名称可更新为“香蕉漫画”，但无必要时不应随意修改已发布的 Key，否则可能造成用户设置、缓存或历史数据无法延续。源顶层 `url` 应是合法更新地址；若没有维护中的更新地址，可显式留空，而不是把不确定的漫画网站页面地址误充当更新地址。[1]

## 3. 全流程工作流：从站点发现到发布

开发必须从站点取证开始，而不是从写代码开始。首先打开首页、搜索页、分类页、漫画详情页和至少两个章节页；分别保存 HTML 或接口响应。随后针对每一类页面找出“内容容器、单项容器、标题、封面、链接、状态、分页、图片数据”的实际字段。只有当这些字段被记录下来，才进入编码阶段。

| 阶段 | 必须做的事实工作 | 必须保存的证据 | 阶段完成条件 |
|---|---|---|---|
| 0. 规范学习 | 查阅 Venera 漫画源与 JS API 文档；阅读官方同类源 | 官方文档 URL、参考源文件名 | 明确返回结构和可用 API |
| 1. 首页取证 | 检查推荐区块、卡片、懒加载封面和详情链接 | 首页 HTML、各选择器、至少一个样本 ID | 能解析多个推荐区块 |
| 2. 搜索取证 | 读取搜索表单 method/action/name；检查结果结构 | 搜索 URL、输入参数、结果 HTML | 至少一个关键词返回正确项目 |
| 3. 分类取证 | 访问分类入口、某一题材页、第二页和状态筛选 | 真实分类 URL、分页链接、卡片数量 | 分类与分页均有真实样本 |
| 4. 详情取证 | 记录标题、封面、简介、标签、章节链接 | 详情 HTML、章节列表节点 | 章节数与页面可见数相符 |
| 5. 图片取证 | 判断图片在 DOM、内联脚本、外链 JS 还是 API 响应 | 章节 HTML、脚本片段、图片/密文样本 | 至少一话得到完整图片列表 |
| 6. 加密判断 | 仅在图片无法直接获得时追踪密文和解密调用链 | 算法、Key/IV、明文格式、成功图片证据 | 可复现解密或明确“未加密” |
| 7. 编码与测试 | 依据取证写脚本和断言 | 源文件、测试脚本、输出日志 | 所有已声明功能通过验证 |
| 8. 发布与维护 | 增加变更日志，标注已验证/待验证能力 | 版本说明、回归结果 | 用户可安全导入并追踪变更 |

## 4. 香蕉漫画案例：真实站点分析记录

### 4.1 首页推荐页

实际访问地址为 `https://www.manhuauo.com/`。首页推荐区块使用 `.mg-section`，区块标题位于 `.mg-section-head h2`。单个漫画卡片使用 `.mg-vod-item`；封面与详情链接位于 `.mg-vod-thumb`，其中 `href` 格式为 `/comic/{id}.html`，封面字段为 `data-original`；标题位于 `.mg-vod-name a`，状态与章节信息分别可从 `.mg-vod-status` 和 `.mg-vod-tag` 提取。

实际样本存在“最近更新”“推荐漫画”“新作上线”“完结漫画”等多个区块，且“最近更新”样本可解析到不少于 10 部漫画。因此最终选择 `singlePageWithMultiPart`，以网站原区块标题作为返回对象键，Venera 探索页显示名称为“香蕉漫画”。

| 字段 | 实际证据 | 源内处理 |
|---|---|---|
| 区块容器 | `.mg-section` | 遍历生成多个推荐区块 |
| 区块标题 | `.mg-section-head h2` | 作为返回对象的键 |
| 漫画项 | `.mg-vod-item` | 单项解析入口 |
| 封面/详情链接 | `.mg-vod-thumb` 的 `data-original`、`href` | 补全 URL，提取漫画 ID |
| 漫画标题 | `.mg-vod-name a` | 写入 `Comic.title` |
| 状态和进度 | `.mg-vod-status`、`.mg-vod-tag` | 合成 `Comic.subTitle` |

### 4.2 分类页

分类入口为 `https://www.manhuauo.com/type/cate/`。真实题材路由不是先前猜测的英文 ID，也不是 `/sort/{数字}`。页面真实链接包括 `/type/cate/恋爱.html`、`/type/cate/纯爱.html`、`/type/cate/都市.html` 等。分类列表仍使用 `.mg-vod-item`，与首页卡片一致。

分类分页也已取证：真实第二页为 `https://www.manhuauo.com/type/cate/恋爱.html?page=2`，实际解析到 **36** 部漫画。页码元素在 `.pagination-list .pagination-link`，因此源应从真实分页节点提取最大数字页码。状态筛选的真实参数为 `?lang=serial` 与 `?lang=end`，分别表示连载和完结。

> **重点：分类路由与分页必须以页面真实链接为准。** 早期脚本使用了未验证的英文参数和 `index{n}.html` 路径，导致分类空列表；修复后改为中文题材 `.html` 路由加 `?page={n}`，并由页面分页控件决定 `maxPage`。

### 4.3 搜索页

搜索表单真实结构为 `method="get"`、`action="/search.html"`、输入字段 `name="wd"`。因此已验证搜索请求为：

```text
GET https://www.manhuauo.com/search.html?wd={encodeURIComponent(keyword)}
```

搜索结果**不使用**首页或分类的 `.mg-vod-item`，而使用 `.mg-search-item`。其中封面与详情链接为 `.mg-search-thumb`，标题为 `.mg-search-name a`，元信息为 `.mg-search-meta`。以关键词“黑执事”实测，解析到一个结果：漫画 ID 为 `8407`，封面相对路径可正确补全为完整 URL。

| 页面类型 | 实际单项选择器 | 标题选择器 | 封面/详情选择器 | 能否与首页复用 |
|---|---|---|---|---|
| 首页 | `.mg-vod-item` | `.mg-vod-name a` | `.mg-vod-thumb` | 可以与分类复用 |
| 分类 | `.mg-vod-item` | `.mg-vod-name a` | `.mg-vod-thumb` | 可以与首页复用 |
| 搜索 | `.mg-search-item` | `.mg-search-name a` | `.mg-search-thumb` | **不可**与首页/分类混用 |

当前没有取得稳定的多页搜索样本，因此“搜索多页 URL 是否为 `&page={n}`”不能写作已证实能力。源可以预留代码路径，但发布日志必须标记为待验证；获得至少两页真实结果的关键词后，必须保存第 1 页和第 2 页 HTML，再根据页面实际分页链接修订并复测。

### 4.4 详情、章节与图片

详情页样本为 `https://www.manhuauo.com/comic/110.html`。标题节点为 `.mg-detail-title`，信息节点为 `.mg-detail-meta li`，章节链接位于 `.mg-chapter-list a`。样本漫画《黄色进化(完结+外传)》解析到 **108** 个章节，章节链接格式为 `/read/110-1-{chapter}.html`。

阅读页样本为 `https://www.manhuauo.com/read/110-1-1.html`。静态 HTML 中未直接输出最终图片 `<img>` 列表；真正图片地址位于内联脚本对象 `player_aaaa` 的 `url` 字段。该字段的格式是用 `|||` 分隔的相对路径，页面前端自身执行 `player_aaaa.url.split('|||')` 后逐张创建图片元素。样本第 1 话解析到 **15** 张图片，首图为：

```text
https://www.manhuauo.com/xinhmg/neirong/2825/125664/0.jpg
```

本案例检查的章节中 `player_aaaa.url` 为明文路径，未发现 AES、RSA、XOR 或自定义 Base64 图片加密。结论不是“该网站永远没有加密”，而是“**本期已取证样本未使用加密**”。后续若出现 `encrypt` 非零、URL 不可读、接口返回密文或图片响应无法直接识别为图像，必须重新走加密取证流程。

## 5. 历次错误、根因与修复决策

开发日志必须记录错误链路，而不是只保留最终可用代码。错误记录能防止后续维护者重复错误，并帮助 AI 在新站点上区分“需要研究”和“可以复用”的部分。

| 错误或风险 | 表现 | 已定位根因 | 正确修复 | 防复发规则 |
|---|---|---|---|---|
| 首页、搜索、分类共用选择器 | 搜索和分类为空 | 将不存在的 `.hl-list-item` 当作所有列表项 | 首页/分类改 `.mg-vod-item`；搜索改 `.mg-search-item` | 每个页面单独保存样本并统计卡片数 |
| 分类路径猜测 | 分类无漫画或分页失效 | 用英文 ID、`index{n}.html` 代替真实链接 | 使用 `/type/cate/题材.html?page=n` | 不从 URL 风格推导路由，直接复制页面链接 |
| 固定或递增最大页数 | 无限加载、请求不存在页 | 使用 `page + 1` 作为 `maxPage` | 从 `.pagination-list` 读取最大页码 | `maxPage` 必须有页面/API 总量依据 |
| 静态 DOM 直接抓图片 | 阅读页返回空图片 | 图片由浏览器运行脚本后才插入 DOM | 解析 `player_aaaa.url` | 先检查内联脚本与网络响应 |
| 无证据引入 AES/XOR | 解密失败、错误复杂化 | 把其他源或长字符串经验套到新站点 | 当前无加密则只做明文 URL 解析 | 加密必须有密文、算法、Key/IV、明文四类证据 |
| 导入“无效参数”风险 | App 拒绝导入或运行异常 | Key 冲突、字段不规范、返回类型不合规 | 采用稳定唯一 Key、`new Comic`、`new ComicDetails`、合规返回结构 | 发布前做脚本加载与对象结构检查 |
| 显示名称不一致 | 分类页显示“分类”而非站点名称 | `category.title` 未同步更新 | 首页和分类标题统一为“香蕉漫画” | 显示名变更写入版本日志，内部 Key 保持稳定 |

## 6. 图片加密与反爬机制：标准判定流程

图片加载问题不等于图片加密问题。开发前应先识别图片数据所处层次：是否是普通 `<img src>`；是否是懒加载属性；是否在内联脚本中；是否来自 JSON 接口；是否为被编码的 URL；还是图片响应本身被加密。只有后两类才需要使用解密 API。

| 现象 | 首先检查 | 可得出结论的最低证据 | 后续动作 |
|---|---|---|---|
| `<img src>` 是真实 URL | 图片标签与实际请求 | URL 请求返回图像 | 直接返回绝对 URL |
| `<img src>` 是 `load.gif` | `data-original`、`data-src`、`srcset` | 懒加载属性含真实路径 | 解析懒加载字段 |
| 页面无图片标签 | 内联 `<script>`、`window` 变量 | 脚本中存在图片数组或 URL 字符串 | 解析脚本变量 |
| 接口返回 Base64 | 返回 JSON 字段与解码结果 | Base64 解码后是 JSON/图像 | `Convert.decodeBase64` |
| 接口/脚本存在 AES 调用 | 站点 JS 的算法、模式、Key/IV 生成 | 明确 AES 模式、密文、Key、IV | 调用匹配的 `Convert.decryptAes*` |
| URL 正常但图片字节乱码 | 图片响应头、前端的响应解密逻辑 | 浏览器脚本对 ArrayBuffer 解密 | 使用 `onResponse(buffer)` 解密 |
| 看到长字符串或混淆 JS | 解包前后代码与运行结果 | 仅长字符串不构成算法证据 | 继续定位解密函数，**禁止猜测** |

> **重点：加密确认的“四证据规则”。** 要将某站点写成“使用 AES-CBC/ECB/XOR”等，至少必须同时具备：①真实密文来源；②站点前端或接口中可追踪的算法调用链；③ Key 与 IV 或 XOR Key 的来源；④解密后能成功得到合法 JSON、URL 或真实图像的验证结果。缺少任意一项，只能标注为“待分析”。

## 7. Venera 官方支持的解密能力与官方参考模式

官方 `Convert` API 提供 Base64 解码、AES-ECB、AES-CBC、AES-CFB、AES-OFB 与 RSA 解密；并提供 UTF-8、MD5、SHA、HMAC、十六进制转换等辅助能力。[2] [3] 这些 API 的存在不代表应当在每个源中调用。算法选择必须服从目标站点的实际证据。

| 已证实的站点机制 | Venera API | 输入要求 | 输出后仍需处理的事项 | 官方参考 |
|---|---|---|---|---|
| Base64 文本/图像数据 | `Convert.decodeBase64(value)` | 确认字段可 Base64 解码 | UTF-8 解码、JSON 解析或图像字节输出 | `ccc.js`、`jm.js` [4] [5] |
| AES-ECB | `Convert.decryptAesEcb(cipher, key)` | 密文 Buffer、Key Buffer、Padding 规则 | 转 UTF-8，校验 JSON/URL | `jm.js` [5] |
| AES-CBC | `Convert.decryptAesCbc(cipher, key, iv)` | 密文、Key、IV 均已取证 | 常见场景需手工去除 PKCS#7 Padding | `ccc.js` [4] |
| AES-CFB | `Convert.decryptAesCfb(cipher, key, blockSize)` | 模式与 blockSize 已确认 | 校验明文格式 | 官方 API [2] |
| AES-OFB | `Convert.decryptAesOfb(cipher, key, blockSize)` | 模式与 blockSize 已确认 | 校验明文格式 | 官方 API [2] |
| RSA | `Convert.decryptRsa(cipher, key)` | RSA Key 与密文来源已确认 | 可能需二次解密/解码 | 官方 API [2] |
| 加密图片响应 | `{ url, onResponse(buffer) }` | 图片请求确实返回加密二进制 | 解密、去 Padding、返回原始图片字节 | `ccc.js` [4] |

官方 `jm.js` 体现了 AES-ECB 的文本解密模式：先从站点密钥派生 Key，再 Base64 解码密文，执行 AES-ECB 解密，最后把结果转为 UTF-8 并截取合法 JSON。[5] 官方 `ccc.js` 则展示 AES-CBC 图片响应解密：先获取并解密会话 Key/IV，再在 `onResponse` 中对图片 ArrayBuffer 解密、去除 PKCS#7 Padding、提取 Base64 图像数据，最后返回图像字节。[4]

对于“漫蛙吧使用 AES”的说法，本期核对的当前官方 `manwaba.js` 直接从 API 返回图片 `item.url`，文件中未调用 `Convert.decryptAes*`。因此不能将“当前官方漫蛙吧源使用 AES”作为本日志的事实。若实际讨论的是历史版本、镜像域名或不同站点分支，必须拿到该版本的真实脚本或网络响应后重新判断。[6]

## 8. 可复用的编码骨架与接口实现原则

实现源时，应将“站点特定内容”封装在几个小函数中，例如 `absoluteUrl`、`comicIdFromHref`、`parseVodItem`、`parseSearchItem`、`parseMaxPage` 和 `getCategoryUrl`。这样当站点改版时，可以只修改特定解析函数，并复用标准的 Venera 返回类型与测试逻辑。

```javascript
// 核心原则示例：每种卡片类型独立解析，避免跨页面猜测复用。
parseSearchItem(item) {
    const thumb = item.querySelector('.真实搜索封面选择器');
    const title = item.querySelector('.真实搜索标题选择器');
    if (!thumb || !title) return null;
    return new Comic({
        id: this.comicIdFromHref(thumb.attributes.href),
        title: title.text.trim(),
        cover: this.absoluteUrl(thumb.attributes['data-original'] || thumb.attributes.src || ''),
        subTitle: item.querySelector('.真实元信息选择器')?.text.trim() || ''
    });
}
```

每个 `HtmlDocument` 在处理结束后应调用 `dispose()`。每个异常捕获分支应返回与 Venera 契约一致的空结构，例如列表返回 `{ comics: [], maxPage: page }`、图片返回 `{ images: [] }`，而不是返回 `null`、字符串或不完整对象。这样可避免将网络失败、选择器失效和返回类型错误混为同一种问题。

## 12. 最终结论

本案例证明，可靠的 Venera 漫画源开发依赖于“取证—实现—验证—记录”的闭环，而不是依赖模板复制或对网站结构、路径和加密方案的猜测。香蕉漫画源最终能够工作，是因为将首页、搜索、分类、详情和图片页面分别取证；修正了错误选择器与错误分页路径；确认图片位于 `player_aaaa.url` 而非静态 DOM；并在最终发布前用真实样本做了完整回归测试。

后续开发任何新源时，应优先复制本日志的流程和验证标准，而不是复制某个站点的具体选择器或加密逻辑。站点特定代码只能从该站点的真实证据中得出；Venera 官方 API 与官方源的作用，是提供已验证的实现模式和能力边界，而不是替代目标站点的逆向分析。

## 附录 A：案例更新——腾讯动漫（正版）的 nonce 干扰 Base64 章节载荷

腾讯动漫移动站为全流程开发日志新增了一个已验证的“**字符干扰 + Base64**”案例。其公开章节请求为 `GET /chapter/index/id/{comicId}/cid/{cid}?style=plain`。响应的第一部分不是可直接 Base64 解码的文本；第二部分将 `window["no"+"nce"]` 赋值为 nonce。站点章节前端脚本将 nonce 中每个 `/\d+[a-zA-Z]+/` 视为“位置 + 要移除的字母干扰字符”：逆序处理这些指令，位置为数字部分与 `255` 按位与，删除长度为字母部分长度；之后才执行 Base64 解码、UTF-8 解码和 JSON 解析。

> **重点：这不是 AES，也不是凭 Base64 前缀就能猜出的协议。** 本案例在真实章节 `id=649514`、`cid=2` 上按前端源代码复现后，得到含 16 项的 `picture` 数组；首图下载后被验证为 800×1149 JPEG。因此该机制应归类为“站点自定义载荷混淆/编码还原”，而非 AES、RSA 或 XOR。

腾讯动漫详情页只直接展示章节预览，完整章节目录位于公开章节页 `#data_chapterInfo` 的 JSON 中。本案例由此得到 448 个去重章节，说明**详情预览节点不等于完整目录数据源**。对正版权限，源仅在 `chapter.canRead !== false` 时返回图片 URL；这既遵守页面明示的权限，也避免把“能解析图片协议”错误地等同于“可以读取付费内容”。详细取证、实现和验证结果见《腾讯动漫（正版）Venera 源专项开发日志》。

| 新增诊断规则 | 已验证动作 | 禁止做法 |
|---|---|---|
| Base64 直接失败 | 读取站点前端数据还原函数与运行时 nonce，再重放字符操作 | 直接改用 AES、XOR 或随机替换字符 |
| 章节目录仅有少量预览项 | 寻找公开章节页/接口中的完整目录 JSON，并以实际数量验证 | 将预览数写作总章节数 |
| 响应中含 `eval` 文本 | 仅解析经白名单限制的必要数字表达式，或由安全实现重放协议 | 执行服务器返回的任意 JavaScript |
| `canRead` 为 false | 返回空图片并提示由官方客户端处理权限 | 规避支付、登录或版权限制 |


### 案例补充：历史阅读与“无效参数”必须独立验证

腾讯动漫（正版）v1.0.1 的修复表明，详情页目录能够阅读并不代表历史页一定能阅读。历史记录可能保存纯章节 ID、完整章节 URL，或 `comicId|chapterId` 一类组合字符串。**`loadEp(comicId, epId)` 必须先将这些形态标准化为站点真实需要的参数，再拼接请求 URL；禁止把未识别的 epId 原样拼到 URL 中。**

对于使用 `Convert.decodeBase64` 的源，载荷还原后应先规范化为标准 Base64：将 URL-safe 的 `-`、`_` 替换为 `+`、`/`，并将长度补齐至 4 的倍数。当前样本即使不需要 Padding，也应保留此防御步骤，以避免其他章节在原生转换层发生“无效参数”一类错误。

> **重点验证规则：发布前至少以“普通目录参数、完整章节 URL 历史参数、组合章节 ID 历史参数、非法参数”四组输入分别执行 `loadEp`。前三组必须返回同一章节的真实图片数量；最后一组必须安全失败且不发出畸形请求。**

### 案例补充：动态 nonce 不能以单话成功作为兼容结论

腾讯动漫 v1.0.3 进一步证明，同一个 `style=plain` 接口可以按章节生成不同的 nonce 属性名拆分方式与数字表达式。已取证的属性名可写成 `no+nce`、`n+once`、`non+ce` 或 `nonc+e`；表达式则至少覆盖基础算术、`charCodeAt`、`substring`、逻辑非、`parseInt`、数字条件表达式、`Math.pow`、按位与、DOM 集合真值、`Math.round` 与 `~~` 截断。它们的共同作用是计算干扰字符删除指令中的数字，**不是要求源执行页面的 `eval`**。

| 响应现象 | 正确处理 | 错误处理 |
|---|---|---|
| `window["n"+"once"]` 等动态赋值 | 还原字符串字面量拼接，确认属性名为 `nonce` 后读取值 | 仅匹配固定 `window.nonce=` 或某一种拆分形式 |
| `eval("...")` 包含无副作用数字表达式 | 为已取证模式建立最小白名单解析器；其余模式安全失败 | `eval`、`Function`、注入浏览器执行返回脚本 |
| 单章可解、另一章“无效参数” | 保存失败 plain 响应，输出原始 nonce 行，比较语法差异后增加最小规则 | 改用随机密钥、把所有错误归为 Base64 Padding |
| 添加一类表达式兼容 | 用多个不同 cid 执行**完整解码**，同时断言章节 ID 和非空图片数组 | 仅对表达式函数写单元测试，未验证删字符与图片数组 |

> **跨章节取样准则：** 动态 nonce 至少应保存三个章节样本；若站点允许，优先覆盖首话、普通中间话、较大 cid 或不同发布时间的章节。每份样本都应保存原始 plain 响应、nonce 行、预期章节 ID、图片数量和首图 URL。实现变更后，必须重新跑所有样本，而不是只跑最近失败的那一话。

受限解析器应遵守“先替换已知无副作用模式，再用自建数字语法树求值”的顺序，并将允许的字符集、运算符、函数和参数类型写死。未知 token、未闭合括号、非数字结果、未识别的 window 属性或不符合 Base64/JSON 预期的数据都必须返回安全失败结果。这样既可以修复协议的已知变体，也不会把“兼容图片加载”变成执行远程脚本的风险。


### 案例补充：历史默认图标通常是已持久化的 `ComicDetails.cover`，不是章节图片故障

Venera 历史列表渲染的是 `History.cover`，而新历史记录的该字段来自 `ComicDetails.cover`。历史页面不会以章节首图或 `thumbnails` 替代漫画封面；因此当详情页误把站点通用 share-icon、favicon 或营销图作为 `cover` 时，历史记录就会保存并长期显示默认图标，即使正文图片 `loadEp` 已经正常。

> **重点排查顺序：** 首先验证 `ComicDetails.cover` 是否为真实漫画封面、是否能返回有效图像字节；其次实现 `onThumbnailLoad`（需要时补充 Referer/User-Agent）；最后必须区分新历史和已保存旧历史。对已保存旧历史，应使用 Venera 的“刷新信息”或“刷新全部历史”重新调用 `loadInfo` 覆盖封面，同时保留阅读进度。

对于含多个 `meta[itemprop="image"]` 的页面，不能假设详情页的第一个元数据就是漫画封面。腾讯动漫案例表明详情页该节点是通用分享图标，实际竖版漫画封面在公开首章节页面；因此开发时须下载并验证最终 `cover` 的 MIME 类型、尺寸和视觉内容后再发布。

## 附录 B：从腾讯动漫（正版）案例提炼的端到端交付规范

本附录不是把腾讯动漫的选择器、域名、参数或 nonce 语法复制到其他站点，而是将该案例中已经验证有效的**工作方法、失败诊断路径和安全边界**抽象为通用规范。Venera 的接口契约仍应以官方漫画源和 JavaScript API 为基准；目标网站的路由、字段、图片协议和权限规则必须重新取证。[1] [2]

### B.1 先区分“页面存在”与“字段可信”

在本次开发中，详情页确实存在 `meta[itemprop="image"]`，但其内容是站点通用分享图，而不是漫画封面；详情页也确实存在章节链接，但只包含目录预览，不是完整目录。这说明 HTML 节点“存在”只能证明解析器找到了一个值，不能证明该值适合写入 Venera 的 `ComicDetails.cover`、`chapters` 或 `loadEp`。

| 字段类别 | 低可信证据 | 可交付的高可信证据 | 必须执行的验证 |
|---|---|---|---|
| 漫画封面 | 页面中第一个 `img`、Open Graph 或 `itemprop=image` | 实际漫画详情/章节页中的作品封面，并可下载为有效图片 | 检查最终 URL、MIME 类型、尺寸与视觉内容；验证历史缩略图请求 |
| 章节目录 | 详情页可见列表 | 公开章节页面、接口或内嵌 JSON 中的完整目录数据 | 对比预览数与完整数，去重后检查首尾章节 |
| 图片数组 | 最长字符串、广告列表或占位 `<img>` | 站点前端真实消费的数据字段或可验证 JSON | 断言图片数、首图 URL 与图片响应 |
| 分页上限 | 固定常量、推测的 `page+1` | 页面分页控件、接口总数或连续终止样本 | 至少验证第 1 页、第 2 页与终止页 |

> **通用结论：** 对用户可见且会被本地数据库持久化的字段，必须执行“来源验证 + 文件/数据验证 + 客户端链路验证”三步。封面写错一次，历史页会持续显示错误值；目录写少一次，用户将无法发现后续章节。

### B.2 用“失败产物”驱动协议分析，而不是用猜测驱动重写

“部分章节成功、部分章节失败”是动态协议存在变体的高风险信号。腾讯动漫案例中，失败并非源于 CDN、网络或单纯 Padding，而是不同章节的 nonce 属性名拆分方式和数字表达式不同。正确做法不是把异常吞掉，也不是直接引入 AES、XOR 或通用 `eval`；而是保留失败输入，并与一个成功输入逐项比较。

| 调试顺序 | 必须保存/输出的内容 | 要回答的问题 | 不应采取的动作 |
|---|---|---|---|
| 1. 保留原始响应 | HTML、JSON、plain、响应头和请求 URL | 失败数据是否与成功数据属于同一接口形态 | 只截取长字符串，丢弃其上下文 |
| 2. 定位协议分界 | 载荷边界、动态赋值行、脚本变量名 | 图片数据、指令数据和广告/占位数据分别在哪里 | 按“最长 Base64”或“第一个脚本变量”猜测 |
| 3. 记录中间态 | nonce、指令列表、还原后长度、Base64 模 4、JSON 顶层字段 | 故障发生在删字符、解码、UTF-8 还是 JSON 阶段 | 只记录最终“无效参数”提示 |
| 4. 比较差异 | 成功与失败样本的属性名、表达式、字段存在性 | 是协议变体、页面改版还是权限分支 | 用单话结果推断全部章节都相同 |
| 5. 最小扩展 | 仅增加已取证语法或字段分支 | 新规则是否足够且没有扩大执行面 | 为方便而执行远程 `eval` 或整个响应脚本 |
| 6. 全量回归 | 新旧全部样本和业务链路 | 修复是否引入其他章节或历史路径回归 | 只重跑最初失败的那一话 |

上述流程适用于动态 nonce、签名参数、分段 Base64、压缩 JSON、轻量混淆和图片响应解密等场景。核心原则是：**每个代码分支必须可追溯到一个原始样本，且每个原始样本必须有可重复的最终断言。**

### B.3 动态协议的安全解析原则

目标站点的前端可能通过 `eval`、字符串拼接或 DOM 真值计算辅助数据，但 Venera 源没有必要、也不应执行这些代码。正确的实现方式是将“协议所需的最小确定部分”转写为受限解析器。例如，只允许已取证的数字、算术、明确的字符串字面量操作和指定函数签名；只允许预定义运算符；对未知 token、非数字结果、未匹配属性名或异常括号立即终止。

| 规则 | 应允许的范围 | 应拒绝的范围 | 验证方式 |
|---|---|---|---|
| 动态字段名 | 已验证的纯字符串字面量拼接，且结果等于预期字段名 | 变量读取、函数调用、任意属性访问 | 断言字段名与样本一致 |
| 数字表达式 | 已取证的常量、有限运算符、显式白名单函数 | `eval`、`Function`、网络/存储访问、任意 DOM 脚本 | 单元断言 + 完整章节解码 |
| 解码指令 | 已取证格式，如“位置 + 字母干扰字符” | 格式不符、越界、缺失数据 | 记录指令数和还原后文本 |
| Base64 | 标准或 URL-safe Base64，补齐可验证 Padding | 无法形成合法 UTF-8/JSON 的盲目重试 | 断言 JSON 的章节 ID、图片数组和首图 |
| 未知变体 | 返回空图片或受控错误并保留样本 | 降级为执行原始脚本 | 标记为待取证，新增样本后再实现 |

> **安全红线：** “图片加载失败”不是执行站点返回 JavaScript 的理由。受限解析器可以扩展，但每次扩展都必须有新样本、最小语法范围、拒绝测试和跨样本回归结果。

### B.4 历史页是独立功能链路，不是阅读页的副产品

Venera 的历史状态会持久化数据。因而新打开章节正常，不等于历史记录能正常恢复；新详情封面正确，也不等于旧历史会自动更新。本次案例确定了两个通用处理方向：其一，`loadEp` 要把普通目录 ID、完整章节 URL 和组合 ID 等历史入参标准化为站点实际所需的参数；其二，历史封面应从 `ComicDetails.cover` 的真实来源修复，必要时用 `onThumbnailLoad` 提供正确请求上下文。

| 历史相关故障 | 典型根因 | 实现要求 | 用户侧必要动作 |
|---|---|---|---|
| 从历史进入章节返回空图或“无效参数” | `epId` 已不是纯章节 ID，被直接拼入 URL | 先解析并校验参数；不合法时不发请求且返回 `{ images: [] }` | 无需清除历史；升级源后重试 |
| 历史封面是站点默认图标 | `ComicDetails.cover` 取到了 favicon、share-icon 或横幅 | 从经验证的真实封面来源填充 `cover` 与 `thumbnails`；按需设置缩略图请求头 | 对旧记录执行“刷新信息/刷新全部历史” |
| 正文图可见但历史封面加载失败 | 图片与缩略图所需 Referer/User-Agent 不同 | 将 `onThumbnailLoad` 作为独立请求链路验证 | 确认刷新后的新封面请求成功 |
| 已付费/不可读章节被错误返回 | 忽略站点显式权限字段 | `canRead === false` 等明确不可读信号必须返回空图 | 由正版官方流程处理权限 |

### B.5 版本升级后的标准验收矩阵

每一次变更都应绑定受影响功能的回归，但图片、目录、封面和历史相关改动还必须执行以下全量矩阵。矩阵中的数字由各站点真实样本决定；不能把腾讯动漫的 448 章、16 图或 7 个 cid 当成其他站点的固定标准。

| 验收层级 | 必测项目 | 通过条件 | 失败时优先检查 |
|---|---|---|---|
| 源契约 | 名称、Key、版本、类加载、返回类型 | 可实例化；Key 稳定；返回 Venera 合规对象 | 顶层字段、类继承、构造器与 Map 类型 |
| 页面链路 | 首页、搜索、分类第 1/2 页、详情 | 数量与样本一致；ID、标题、封面有效 | 真实路由、选择器、懒加载字段、分页来源 |
| 目录链路 | 预览与完整目录 | 完整数经真实节点/接口验证且去重 | 公开章节页、脚本变量、JSON 节点 |
| 封面链路 | `cover`、`thumbnails`、缩略图请求 | 真实漫画图片可读且请求上下文有效 | 通用图标、相对 URL、Referer/User-Agent |
| 章节链路 | 普通参数、历史 URL、组合 ID、非法参数 | 前三者结果一致；非法参数不请求且安全失败 | 参数标准化、URL 拼接、异常返回结构 |
| 动态协议 | 至少 3 份跨章节样本 | 每份的章节 ID、图片数组、首图均正确 | 原始 nonce/字段行、表达式白名单、解码中间态 |
| 权限与安全 | 不可读分支、未知表达式 | 不返回受限图片；未知语法不执行 | 权限字段、解析器拒绝逻辑 |
| 发布 | 自动回归和真实客户端导入 | 自动测试全绿；客户端状态单独记录 | JavaScript 引擎差异、缓存和旧历史数据 |

# 新案例：动漫啦（www.dongman.la）源开发经验

> 本节记录的是可复用的方法和本案例的真实证据。站点 URL、CSS 选择器、漫画 ID、图片 CDN 路径和页数只能作为本案例事实，不能未经取证复制到其他漫画源。

## C.1 同一站点可能同时存在多套页面模板

动漫啦的首页、分类/搜索页和详情/阅读页并非完全使用同一套 DOM。首页推荐区使用 `.cy_wide_list > ul > li`，分区标题位于 `span a`，卡片标题位于 `b a`；分类页和搜索页使用 `.cy_list_mh > ul`，标题位于 `.title a`，状态位于 `.zuozhe`，标签位于 `.biaoqian`，简介位于 `.info`；详情页使用现代属性选择器，例如 `h1[itemprop=name]`、`img[itemprop=image]` 和 `#chapterList`。

这说明不能只从一个页面复制选择器到全部功能。首页推荐、分类列表、搜索结果和详情页必须分别保存 HTML，并分别建立字段映射表。列表解析器也应拆成 `parseWideCard` 和 `parseListCard` 等专用函数；只有在真实 DOM 证实完全一致时，才可以共用解析器。

| 页面功能 | 真实容器 | 标题字段 | 封面字段 | 取证结论 |
|---|---|---|---|---|
| 首页分区 | `.cy_wide_list` | `b a` | `img[data-src]` 或 `img[src]` | 需要单独解析 |
| 分类页 | `.cy_list_mh > ul` | `.title a` | `img[src]` | 可复用到搜索页 |
| 搜索页 | `.cy_list_mh > ul` | `.title a` | `img[src]` | 与分类页一致 |
| 详情页 | `article` / Schema 属性 | `h1[itemprop=name]` | `img[itemprop=image]` | 不能使用列表卡片选择器 |
| 章节页 | 阅读容器内 `img` | 页面标题和页码 | `img[src]` | 直接提取图片 URL |

## C.2 不能把“直链图片”误判成加密协议

本案例对一拳超人、全职猎人等多个真实章节进行原始响应和图片二次请求检查。章节页直接返回 `img[src]`，例如一拳超人第 256 话的图片为 `https://img.dongman.la/y/yqcr/256/0001.jpg`；图片请求返回 HTTP 200、`image/jpeg`，文件头为标准 JPEG `FF D8 FF E0`。封面也直接返回标准 JPEG。

因此本源没有加入 AES、XOR、Base64、nonce 或任意 JavaScript 执行逻辑。这是一个重要的负面结论：**没有加密证据时，最可靠的实现是保留原始图片绝对 URL，而不是为了“兼容加密”加入猜测性解密。** 后续如果图片失效，必须重新保存失败响应，比较 HTTP 状态、Content-Type、文件头、Referer 和页面脚本后再修改。

## C.3 普通分页页与整话页应分开取证

普通阅读页只包含当前页图片，同时预加载下一页或下下页；例如 `/manhua/chapter/5985/395258/` 显示第 1 页，并预加载 `0002.jpg` 与 `0003.jpg`。整话页 `/manhua/chapter/5985/395258/all.html` 一次包含 17 个图片节点。因此章节实现优先请求整话页并解析全部 `img[src]`，失败时再回退到普通页。

这一策略适用于服务端生成的分页漫画站，但必须满足两个条件：一是整话路由已通过真实响应确认，二是图片节点已去重。不能仅凭 URL 中的 `all` 猜测路由；也不能把普通页的预加载图片误认为完整章节。验收时应同时断言整话图片数量、首图、尾图和唯一性。

## C.4 搜索分页必须记录“未验证”而不是伪造支持

动漫啦搜索表单真实 action 为 `/manhua/search/`，参数名为 `key`。搜索第 1 页 `/manhua/search/?key=一拳超人` 正常返回 6 条结果；候选 `/manhua/search/2.html?key=一拳超人` 返回 404，加入 `page=2` 仍返回第 1 页内容。因此本源只把搜索第 1 页作为已验证功能，未把无证据的分页路径写成确定规则。

这条经验应加入所有源的发布验收：如果真实站点没有可用的第 2 页，不要为了满足接口形式而返回虚假的 `maxPage`；可以安全地返回 `maxPage: 1`，或者在源码和日志中明确“搜索分页待取证”。

## C.6 可复用的源开发检查项

1. 在写源之前分别保存首页、分类、搜索、详情和章节原始 HTML，并为每个页面建立选择器表。
2. 先检查图片响应的状态码、Content-Type 和文件头，再决定是否需要解密；标准 JPEG/PNG 响应不应添加未经证实的解密。
3. 对服务端分页阅读站点，分别验证普通页、下一页、整话页和跨章节页；优先使用已确认的整话页，但保留单页回退。
4. `loadInfo` 的章节 Map key 使用站点稳定 ID，而不是只使用可变章节显示名称；这样更有利于历史记录恢复。
5. 对首页、分类和搜索采用各自的真实 DOM 解析器；同一站点模板变化时，优先局部修复而不是扩大正则兜底。
6. 对未验证的分页、备用域名和图片加密方式明确记录为限制，不在源中伪造支持。
7. 交付前至少执行：源语法检查、首页、搜索、分类、详情、章节、跨漫画、封面请求、图片去重和请求头回归。

## C.8 搜索入口 302 重定向的修复经验

动漫啦案例进一步证明：**搜索表单 action 不一定是最终可解析页面**。本次表单显示 action 为 `/manhua/search/`，但真实请求 `/manhua/search/?key=一拳超人` 返回 HTTP 302，最终搜索页位于 `/manhua/so/一拳超人/`。当源依赖网络层自动跟随重定向时，可能因 Venera 版本、请求实现或站点响应差异而得到空响应或仅得到重定向提示文本，最终表现为“搜索不能用”。

| 检查项 | 错误做法 | 推荐做法 |
|---|---|---|
| 表单 action | 直接把 action 当最终列表页 | 用真实 HTTP 响应检查 30x Location |
| 重定向 | 假设 `Network.get` 一定跟随 301/302 | 对关键入口取证最终 URL，源直接请求已确认的最终路由 |
| 搜索结果 | 只测试页面标题或状态码 | 同时断言结果容器、首项 ID、封面和结果数量 |
| 分页 | 使用调用方 page 自动拼接未经验证的参数 | 只有真实页面存在页码时才返回对应 `maxPage` |
| 编码 | 仅测试 ASCII 关键词 | 至少测试一个中文关键词，并检查 URL 编码后的最终路由 |

可复制的搜索诊断顺序是：先记录源实际请求 URL，再用原始 HTTP 客户端检查状态码、Location、最终 URL 和响应字节；随后分别请求旧入口和最终入口，比较 HTML 中结果卡片数量；最后在源测试中加入“最终 URL 精确断言”。如果旧入口返回 30x 而最终入口稳定返回 200，应优先改为最终入口，而不是添加更宽泛的 HTML 正则或猜测式回退。

动漫啦 v1.0.1 的修复结果是：`buildSearchUrl("一拳超人")` 直接返回 `/manhua/so/%E4%B8%80%E6%8B%B3%E8%B6%85%E4%BA%BA/`，真实响应包含 6 条搜索结果；首页、搜索、分类、详情、章节目录和图片回归全部通过。该规则可复用于其他服务端渲染漫画站，但具体 URL 必须每站重新取证。


## C.9 搜索故障的完整证据链与经验教训

动漫啦 v1.0.1 的搜索故障应作为“请求入口与最终数据入口分离”的典型案例保留。初版源根据表单 action 请求 `/manhua/search/?key={关键词}`，离线测试桩又直接把该 URL 映射到搜索 HTML，因此初始回归没有暴露问题；但真实请求返回 HTTP 302，Location 指向 `/manhua/so/{关键词}/`，响应体只有短重定向提示。若运行环境没有自动跟随 302，解析器接收到的就不是 HTML，自然得到空搜索结果。

> **通用结论：** “选择器正确”只说明拿到完整 HTML 后可以解析，不说明请求链路一定拿到了完整 HTML。搜索验收必须同时验证请求 URL、状态码、重定向、响应字节和结果字段。

| 证据层 | 必须记录的内容 | 动漫啦案例 |
|---|---|---|
| 源构造 | 源实际生成的完整 URL | 初版为 `/manhua/search/?key=...`，修复后为 `/manhua/so/.../` |
| 首次响应 | HTTP 状态、Content-Type、响应字节 | 302，约 5 字节重定向体 |
| 跳转信息 | Location 的完整值 | `/manhua/so/一拳超人/` |
| 最终响应 | 状态、HTML 长度和结果容器 | 200，约 11 KB，含 `.cy_list_mh` |
| 业务字段 | 结果数量、首项 ID、封面 | 6 条，首项 ID `5985` |
| 客户端契约 | `maxPage` 和分页是否真实存在 | 当前搜索分页未取证，固定以 1 页为边界 |

### C.9.1 搜索故障的标准排查顺序

以后遇到搜索无结果时，不能直接修改 CSS 选择器。第一步是输出源实际请求 URL；第二步是用原始 HTTP 请求检查 30x、Location、最终 URL、Content-Type 和响应字节；第三步是分别请求旧入口和最终入口，确认哪个响应真正包含结果卡片；第四步是使用中文关键词检查编码；第五步才检查 HTML 选择器、懒加载字段和分页节点。每一步都应保存原始响应或摘要，避免只凭浏览器页面观感判断。

### C.9.2 离线测试桩的限制

本案例的初始离线测试桩把旧搜索入口直接映射到已保存的结果 HTML，等价于替网络层自动跟随了 302，因此测试通过并不能代表真实客户端通过。对于存在重定向、Cookie、Referer、Cloudflare 或分页跳转的站点，测试桩必须显式模拟真实网络行为，或者至少对源最终构造的 URL 做精确断言。推荐的搜索回归断言包括：最终 URL、中文关键词编码、结果数量、首项 ID、封面域名、空响应处理和真实 `maxPage`。

### C.9.3 修复边界与防止过度修复

本次应修复的是请求入口，而不是加入更多解析兜底。只有在真实最终 HTML 证实 DOM 变化时，才扩展选择器；只有在真实图片响应证实加密时，才添加解密；只有在真实分页链接存在时，才返回大于 1 的搜索 `maxPage`。未经取证的备用域名、分页 URL、动态脚本执行和“最长字符串”兜底都不应加入源。

### C.9.4 发布验收新增项目

| 新增验收项 | 通过条件 |
|---|---|
| 表单与最终入口 | action、首次状态和 Location 已记录；源请求稳定最终 URL |
| 重定向兼容 | 不依赖 Network.get 自动跟随 301/302 |
| 中文关键词 | 至少一个中文词生成正确编码路径并返回结果 |
| 短响应拒绝 | 5 字节重定向提示、空响应或错误页不会被当作搜索 HTML |
| 离线桩真实性 | 测试桩不会静默替换真实跳转行为 |
| 分页真实性 | 未取证的搜索分页不返回虚假 maxPage |
| 修复后全链路 | 搜索修复不能破坏首页、分类、详情、章节和图片 |

动漫啦 v1.0.1 通过上述新增检查：搜索“一拳超人”返回 6 条真实结果，首页、分类、详情、263 个章节和章节图片回归继续通过。该案例应被复用于后续所有新源的搜索功能开发，但具体最终 URL 必须重新取证。

# 附录 D：面向 AI 的新网站 Venera 漫画源全流程开发规范

> 本附录解决的不是某一个网站的选择器问题，而是“给 AI 一个新网址后，如何让它知道必须查找什么、必须实现什么、必须验证什么”。任何新站点都必须按本附录执行；站点特定的 URL、CSS 选择器、图片域名、章节 ID、加密算法和密钥仍然必须重新取证。

## D.1 交付目标：不是生成代码，而是生成可验证的完整功能链

一个新源只有在首页推荐、搜索、分类、漫画详情、完整章节目录、章节图片、封面/缩略图、历史阅读参数和客户端导入均得到相应证据后，才可以称为“完成”。能打开首页、能解析一张漫画或能通过 JavaScript 语法检查，都不足以证明源可用。

> **强制原则：先取证，后建模；先实现，后编译；先真实回归，后交付。任何未验证能力必须写成“待验证”，不能写成“已支持”。**

| 完成等级 | 必须满足的条件 | 是否允许交付 |
|---|---|---|
| L0：站点可达 | 首页可访问，或已取得用户提供的 HTML/HAR/响应 | 不允许生成可用源 |
| L1：结构取证 | 首页、搜索、分类、详情、章节和图片层次已有真实样本 | 只允许提交分析，不允许宣称完成 |
| L2：源可加载 | 类、Key、版本、API 返回结构和语法检查通过 | 仍不允许宣称功能完整 |
| L3：本地真实样本通过 | 首页、搜索、分类、详情、章节和图片回归通过 | 可提交候选源，必须标注客户端待验证项 |
| L4：客户端验收通过 | Venera 实际导入，分类和章节详情可打开，图片和历史路径正常 | 才能作为稳定源交付 |

## D.2 新网站任务的强制启动协议

AI 收到一个新网站 URL 后，第一步不是写 JavaScript，而是建立“站点证据档案”。档案至少包含目标 URL、站点显示名称、当前可访问域名、HTTP/HTTPS 跳转、移动端与桌面端差异、响应状态、Content-Type、字符集、UA/Referer 要求、登录/地区/Cloudflare 拦截情况和取证时间。

如果网站返回 403、验证码、区域禁止、登录页、空白壳页面或无法稳定获取正文，AI 必须停止猜测选择器和图片协议，并向用户请求可访问网络中的 HTML、HAR 或页面响应。第三方旧书源、搜索引擎摘要、相似域名和历史代码只能作为待验证线索，不能直接作为当前实现依据。

### D.2.1 启动阶段必须回答的问题

| 问题 | 必须记录的答案 |
|---|---|
| 站点实际名称是什么 | 页面 `<title>`、Logo 文本、页脚名称和用户指定名称是否一致 |
| 当前最终域名是什么 | 原始 URL、最终 URL、重定向 Location 和备用域名关系 |
| 页面是否可达 | 状态码、响应字节、Content-Type、是否为错误页/登录页 |
| 是否需要请求上下文 | User-Agent、Referer、Cookie、Accept、移动端标识 |
| 是否存在多套模板 | 首页、搜索、分类、详情、章节是否使用不同 DOM |
| 是否涉及权限边界 | 付费、登录、版权地区限制、`canRead` 或其他明确字段 |
| 证据保存在哪里 | HTML、JSON、脚本、图片、响应头、截图和测试输出路径 |

## D.3 强制页面证据矩阵

新源开始编码前，必须尽可能保存下表中的真实样本。若某一项不可访问，必须在日志中标记阻断原因和替代证据；不能默认为“与其他页面相同”。

| 编号 | 必须取证的页面 | 最低样本要求 | 必须记录的字段 | 完成门槛 |
|---|---|---|---|---|
| P1 | 首页 | 首页原始 HTML 和至少 5 个卡片 | 分区、标题、详情链接、封面、最新章节、懒加载字段 | 能解析至少一个分区和多个 Comic |
| P2 | 搜索第 1 页 | 一个中文关键词、一个英文/数字关键词或空结果 | method、action、字段名、首次状态、Location、最终 URL、结果卡片 | 结果首项 ID、标题、封面正确 |
| P3 | 分类第 1 页 | 全部/地区/题材/状态中至少两个真实分类 | 分类名称、参数、URL、卡片、总页/分页 | 至少一个分类可返回 Comic 列表 |
| P4 | 分类第 2 页或终止页 | 真实第二页；若没有则保存终止证据 | 页码链接、maxPage、重复项、终止状态 | `maxPage` 有页面/API依据，不使用 `page+1` |
| P5 | 漫画详情 | 至少一部章节较多的漫画 | 标题、可信封面、作者、简介、地区、状态、标签、章节节点 | `ComicDetails` 字段和章节 Map 可构造 |
| P6 | 最新章节 | 最新话原始响应 | 章节 ID、标题、页数、图片字段、权限字段 | `loadEp` 返回非空真实图片 |
| P7 | 中间章节 | 与最新章节不同的章节 | 同上，比较字段和图片协议 | 证明协议不是只适用于一话 |
| P8 | 较早章节 | 较早或特殊章节 | 同上，检查旧路由/旧图片命名 | 证明章节参数和图片规则可跨样本 |
| P9 | 整话/单页阅读页 | 若站点存在两种模式则都保存 | 普通页、整话页、预加载、上一页/下一页 | 不把预加载图片误认为完整章节 |
| P10 | 真实图片二进制 | 封面 1 张、章节图至少 2 张 | 状态、Content-Type、文件头、尺寸、视觉内容 | 证明 URL 可读或证实加密 |

### D.3.1 证据文件命名规范

建议按以下方式保存，便于 AI 和后续维护者自动定位：

```text
{project}/
  research_notes.md
  responses/
    home.html
    search_page1.html
    category_all_page1.html
    category_all_page2.html
    detail_{comicId}.html
    chapter_{comicId}_{chapterId}_latest.html
    chapter_{comicId}_{chapterId}_middle.html
    chapter_{comicId}_{chapterId}_old.html
    chapter_{comicId}_{chapterId}_all.html
  headers/
  images/
  scripts/
  tests/
  source_{version}.js
  development_log.md
```

每一份样本旁边都应记录请求 URL、最终 URL、状态码、响应字节、UA/Referer、取证时间和证据等级。只保存截图而不保存原始 HTML，通常不足以定位选择器、重定向和图片协议问题。

## D.4 页面建模：每一类页面必须独立分析

AI 不得假设首页、分类、搜索和详情共用选择器。即使页面视觉上都是漫画卡片，搜索结果也可能使用另一套容器；首页可能使用 `data-src`，分类页使用 `src`，详情页可能使用 Schema 元数据；章节页可能完全没有 `<img>`，而把图片放进脚本变量或 API。

| 页面 | 必须建立的字段模型 | 常见误区 |
|---|---|---|
| 首页 | 分区标题、分区容器、卡片、标题、详情 ID、封面、最新章 | 只返回一个区块，忽略首页其他推荐区 |
| 搜索 | 表单、输入名、method/action、30x 跳转、结果卡片、空结果 | 将表单 action 直接当最终 HTML URL |
| 分类 | 分类名称与参数对应、分页、状态筛选、总页 | 猜测 `/sort/{id}`、固定 maxPage、未实现分类 |
| 详情 | 标题、真实封面、简介、元数据、完整章节列表 | 把 share-icon 当封面，把预览目录当完整目录 |
| 章节 | 章节 ID、页数、权限、图片数据来源、整话/单页模式 | 用显示标题代替稳定 ID、只测试最新章 |
| 图片 | URL、请求头、响应头、文件头、尺寸、解密状态 | 看到长字符串就猜 AES/XOR，抓到广告/占位图 |

### D.4.1 字段可信度规则

用户可见字段必须经过三层验证。第一层是来源验证：确认字段来自真实详情、章节、接口或站点前端消费的数据；第二层是数据验证：封面必须能下载为图像，章节目录必须包含真实章节 ID，图片数组必须去重且可请求；第三层是客户端链路验证：`ComicDetails.cover` 应能进入历史封面，章节 Map key 应能传给 `loadEp`，缩略图应能通过 `onThumbnailLoad` 加载。

一个节点存在不等于它就是正确字段。页面中第一个 `meta[itemprop=image]`、最长 Base64 字符串、首个 `<img>`、第一个章节链接和最大数字页码都必须经过语义和响应验证后才能采用。

## D.5 搜索功能的强制实现与验收

搜索是独立功能链路，必须从站点表单和真实网络响应开始。AI 必须记录 `method`、`action`、输入字段名、默认值、中文关键词编码、空关键词行为、无结果页面、首次 HTTP 状态、`Location`、最终 HTML URL、结果容器和分页链接。

特别要检查：表单 action 是否返回 301/302；Network.get 是否在当前 Venera 环境跟随重定向；最终 URL 是否需要路径编码而不是 query 参数；站点是否对中文路径进行二次解码；搜索结果是否和分类使用不同 DOM。

最低搜索验收必须包括：一个中文关键词返回有效结果，一个不存在的关键词返回安全空结果，一个结果卡片的 ID、标题和封面正确；如果声称支持分页，还要对第 1 页、第 2 页和终止页做真实验证。如果第 2 页未取证，必须返回真实边界或标记待验证，不得把调用方的 page 参数自动当作 maxPage。

## D.6 分类功能是硬性要求，不是可选增强

新 AI 生成的源经常只有首页和搜索，分类完全缺失或分类按钮点击后为空。为避免这一问题，分类必须在任务开始时建立“分类名—站点参数—真实 URL—分页规则”四列映射表，并在源码的 `category.parts` 中一一对应。

至少应优先实现站点导航中真实存在的一组分类，例如“全部/日本/港台/欧美/国产”“题材”“连载/完结”。如果网站没有传统分类，也必须实现站点实际提供的筛选、标签、状态或排行榜入口，并在日志中说明证据。

| 分类检查 | 强制条件 |
|---|---|
| 分类名称 | `category.title`、part name 和用户可见名称一致 |
| 参数对应 | categories 与 categoryParams 长度一致、顺序一致 |
| 分类请求 | 每个首批分类参数能生成真实 URL |
| 列表解析 | 返回至少一个非空 `Comic[]`，ID/标题/封面有效 |
| 分页 | 第 1 页和第 2 页或终止页真实可访问 |
| maxPage | 来自分页节点、API 总量或可靠终止证据 |
| 状态筛选 | 连载、完结或网站等价筛选至少取证一项 |
| 回归 | 至少两个分类参数和一个分页样本通过 |

如果分类页面需要 POST、筛选参数、排序参数或 JavaScript 生成 URL，必须保存请求样本并在日志写出完整参数；不能只把导航文字写进 `category` 而不实现 `categoryComics.load`。

## D.7 章节详情功能是硬性要求，不是“有章节链接”就算完成

章节详情打不开通常不是章节列表没有链接，而是详情返回的章节 key、loadEp 接收的参数和网站实际阅读 URL 三者不一致。实现后必须验证以下契约：

```text
ComicDetails.chapters Map key
        ↓
comic.loadEp(comicId, epId)
        ↓
站点实际章节 URL/请求参数
        ↓
章节 HTML/JSON/脚本
        ↓
真实图片数组
```

章节 Map 的 key 应优先使用站点稳定的章节 ID；如果 Venera 历史可能保存完整 URL、文件名或组合值，`loadEp` 必须先做标准化。普通目录 ID、完整章节 URL、仅文件名、组合章节 ID 和非法/缺失参数都要加入回归矩阵。前三类若是站点允许的历史形态，应指向同一章节；非法参数必须安全返回空图片数组且不发出畸形请求。

至少要用最新、中间、较早三个章节测试 `loadEp`。每一话应断言章节响应成功、图片数非零、首图正确、尾图存在、图片 URL 去重、图片响应可读；如果站点有权限字段，还要分别验证可读和不可读分支。

章节详情的最低验收表如下：

| 项目 | 必须确认 |
|---|---|
| 详情页 | 标题、可信封面、简介和章节 Map 非空 |
| 章节 ID | Map key 可还原真实阅读 URL |
| 最新章节 | `loadEp` 可返回真实图片 |
| 中间章节 | 与最新章节使用同一或已解释的协议 |
| 较早章节 | 旧路径、旧命名或特殊话不导致空图 |
| 整话模式 | 若已取证，优先解析完整章节而非预加载节点 |
| 普通模式 | 若无整话页，单页回退逻辑可工作 |
| 历史参数 | URL、文件名、组合 ID 和非法参数均有结果断言 |
| 权限 | 明确不可读时不返回受限图片 |

## D.8 封面、缩略图与历史必须单独验收

章节图片能打开，不代表漫画封面能打开；详情页封面能打开，也不代表历史页保存的是正确封面。`ComicDetails.cover` 是历史封面的关键来源，必须从真实漫画封面字段获得；不能使用 favicon、share-icon、网站 Logo、文章头图或章节首图替代，除非取证确认它们就是作品封面。

至少应对封面执行 HTTP 状态、Content-Type、文件头、尺寸和视觉内容检查。若封面或缩略图需要 Referer、User-Agent、Cookie 或解密，应实现并验证 `onThumbnailLoad`；正文图片的 `onImageLoad` 不能自动代表缩略图链路已经正确。

旧历史记录可能已经持久化错误封面。日志和发布说明必须写出用户动作，例如“刷新信息”或“刷新全部历史”，并明确这不是正文图片修复失败。

## D.9 图片协议和加密的强制判定流程

图片分析必须按以下顺序进行：

1. 检查章节 DOM 中的 `src`、`data-src`、`data-original`、`srcset` 和懒加载占位图。
2. 检查内联脚本、全局变量、JSON-LD、播放器对象和外链脚本引用。
3. 检查 Network 响应的 JSON 字段、Base64 文本、压缩内容或 ArrayBuffer。
4. 下载一张封面和两张章节图片，检查状态、Content-Type、文件头、尺寸和视觉内容。
5. 只有在确认图片不是普通图像时，才追踪 AES、RSA、XOR、Base64、nonce、签名或自定义混淆。

加密实现必须同时具有四类证据：真实密文来源、前端/接口算法调用链、Key/IV/XOR Key 来源、解密后合法 JSON/URL/图像的成功结果。不能因为图片加载失败、页面含 `eval`、存在很长的字符串或其他站点用了 AES，就在新源中添加解密。

任何站点响应中的 `eval`、`Function` 或未知脚本都禁止直接执行。对动态协议只能建立最小白名单解析器；未知 token、未知属性、异常括号、非数字结果和解码后非 JSON/非图片数据都应安全失败。

## D.10 源代码实现和“编译”检查清单

Venera 漫画源通常是 JavaScript 源文件，不应把“文件保存成功”当作编译成功。交付前至少要完成以下静态和运行时检查：

| 检查类别 | 必须执行的检查 |
|---|---|
| 语法 | `node --check` 或等效 JavaScript 语法检查 |
| 类加载 | 在 Venera 兼容桩或应用中实例化源类 |
| 元数据 | name、key、version、minAppVersion、url 合法；key 稳定且不冲突 |
| API 类型 | `Comic`、`ComicDetails`、章节 Map、列表和图片返回类型正确 |
| 文档对象 | 每个 HtmlDocument 完成后调用 `dispose()` |
| 异常返回 | 列表返回 `{ comics: [], maxPage }`，图片返回 `{ images: [] }`，不返回 null/字符串 |
| URL | 相对 URL、绝对 URL、协议相对 URL、重复斜杠和编码路径正确标准化 |
| 安全 | 无 `eval`、`Function`、任意远程脚本执行和未经取证的解密兜底 |
| 调试 | 删除或隔离临时 debug 输出，不吞掉必要的错误证据 |
| 版本 | 修复递增 version，非必要不修改 key，日志与源版本一致 |

“编译通过”只表示脚本可以加载，不表示站点功能可用。编译后必须继续执行真实 HTML/JSON 样本回归；如果只有语法检查而没有真实样本断言，交付等级最高只能是 L2。

## D.11 强制真实回归矩阵

新源交付前，必须生成一个可重复的回归脚本或明确的命令步骤。测试应使用保存的真实响应，不能只使用人工构造的简化 HTML；如果使用 mock，必须记录真实请求 URL、真实状态码/重定向和真实响应体边界。

| 层级 | 必测项目 | 通过标准 |
|---|---|---|
| 源契约 | 类、name、key、version、返回类型 | 可加载、可实例化、无导入错误 |
| 首页 | 推荐分区、多个卡片、封面和详情 ID | 区块非空，至少多个 Comic 字段正确 |
| 搜索 | 中文关键词、无结果关键词、最终 URL | 有效结果和安全空结果；不依赖未验证重定向 |
| 分类 | 两个分类参数、第 1/2 页或终止页 | 分类非空，分页和 maxPage 有依据 |
| 详情 | 标题、封面、元数据、章节数 | ComicDetails 正确，章节 Map 非空 |
| 章节 | 最新、中间、较早三话 | 三话均有真实图片，首尾和数量正确 |
| 图片 | 封面、章节首图、章节尾图 | HTTP/文件头/视觉内容可验证 |
| 历史 | ID、完整 URL、文件名、组合 ID、非法值 | 合法值一致；非法值安全失败 |
| 权限 | 可读和不可读分支 | 不越过站点明示权限 |
| 跨页面 | 首页卡片、搜索卡片、分类卡片进入同一详情 | ID 和封面一致，详情可打开 |
| 安全 | 未知动态表达式/未知解密分支 | 不执行远程代码，安全返回 |
| 客户端 | Venera 实际导入和点击链路 | 分类、搜索、详情、章节图片可用 |

回归输出必须保存“通过/失败/待验证”三态，而不是只打印一个总成功。若某项失败，交付说明必须写清是请求、编码、选择器、数据字段、权限、图片 CDN、解密、Venera 契约还是客户端缓存问题。

## D.12 失败排查矩阵

| 用户现象 | 第一检查点 | 第二检查点 | 禁止的仓促修复 |
|---|---|---|---|
| 搜索无结果 | 实际 URL、30x、Location、最终 HTML | 输入编码、结果容器、空结果页 | 直接换成猜测的搜索路径 |
| 分类按钮为空 | categoryParams 与真实 URL | 分类卡片、分页、状态参数 | 只写分类名称不实现 loader |
| 分类只能第一页 | 第二页真实 href、maxPage 来源 | 相对 URL 和 page 参数 | 用 `page+1` 固定最大页 |
| 详情页打不开 | 详情 URL、HTTP 响应、ID 清理 | h1、封面、章节容器 | 只改 CSS 选择器，忽略 URL 拼接 |
| 章节详情空图 | Map key、epId 标准化、实际章节 URL | 普通页/整话页/脚本/API | 把完整 URL 再套一层 host |
| 只有最新章节能读 | 对比最新/中间/较早原始响应 | 动态字段、旧路径、权限 | 只增加一个硬编码章节特例 |
| 封面错误/默认图 | ComicDetails.cover 来源、图片文件头 | onThumbnailLoad、历史持久化 | 用章节首图或网站 Logo 强行替代 |
| 图片显示占位图 | data-src/data-original/srcset | 图片响应和懒加载脚本 | 抓取最长字符串或广告列表 |
| 图片“无效参数” | Base64 padding、URL-safe字符、请求参数 | 真实 nonce/Key/IV/返回类型 | 直接改用 AES/XOR/eval |
| 本地测试通过但 App 失败 | Venera API 签名、重定向、JS 引擎差异 | 真实客户端导入和历史数据 | 认为 mock 通过等于客户端通过 |
| 历史页章节失败 | 历史保存的 epId 形态 | loadEp 标准化和安全失败 | 清空历史或只改详情页 |

## D.13 AI 必须执行的阶段闸门

为了避免 AI 在缺少证据时继续生成代码，每个阶段都设置停止条件：

| 闸门 | AI 必须回答的问题 | 未满足时的动作 |
|---|---|---|
| G1 可达闸门 | 我是否拿到了目标站真实 HTML/响应，而不是错误页或摘要？ | 请求用户提供 HTML/HAR，停止猜测 |
| G2 结构闸门 | 首页、搜索、分类、详情、章节和图片各自的容器是否已确认？ | 继续取证，不写完整源 |
| G3 契约闸门 | 我是否确认了 Venera 类、返回类型和 API 签名？ | 阅读官方文档/同类源，先做最小加载 |
| G4 功能闸门 | 分类和章节详情是否都已有真实 URL、参数和样本？ | 不允许只交付首页/搜索源 |
| G5 协议闸门 | 图片是直链、懒加载、脚本、JSON 还是加密二进制？ | 保存原始样本，不凭经验加解密 |
| G6 编译闸门 | 源能否语法检查、类加载和对象实例化？ | 修复导入/类型问题后再回归 |
| G7 真实回归闸门 | 首页、搜索、分类、详情、三话章节、封面和历史入参是否通过？ | 标记失败/待验证，不得宣称完成 |
| G8 交付闸门 | 源、测试、专项日志、主日志和限制说明是否齐全？ | 补齐交付物，禁止只发源文件 |

## D.14 可直接复制给新 AI 的完整任务模板

```text
请按照《Venera 漫画源端到端开发日志》为以下网站开发一个新的 Venera 漫画源：{目标网址}。

你必须遵守以下流程，不得跳过取证直接写代码：

第一阶段：检查目标站可达性。记录最终 URL、HTTP 状态、Location、Content-Type、字符集、响应字节、UA/Referer 要求和站点名称。如果只能得到 403、验证码、登录页、区域限制或错误页，请停止猜测并向我索要可访问网络中的 HTML/HAR。

第二阶段：分别保存并分析首页、搜索第1页、至少两个真实分类、第2页或终止页、漫画详情、最新章节、中间章节、较早章节、整话/单页阅读页和至少三张真实图片。每份样本写入证据清单，记录实际 URL、选择器、字段、样本数量和保存路径。

第五阶段：分析图片协议。先检查 img、懒加载属性、内联脚本、JSON/API、图片响应和文件头。只有同时有密文、算法调用、Key/IV或XOR Key来源、解密后合法图片四类证据时才实现解密。禁止 eval、Function、任意执行站点脚本和未经证实的 AES/XOR/Base64 兜底。

第六阶段：执行 node --check/等效编译、类加载和对象契约检查。每个 HtmlDocument dispose；异常返回 Venera 合规空结构；URL、编码、相对路径、完整 URL、重复斜杠和历史参数必须标准化；版本递增但非必要不改变 key。

第八阶段：交付源文件、回归脚本或命令、专项开发日志、主日志更新和发布说明。发布说明必须使用“通过/失败/待验证”三态，写出根因、修复、真实样本、测试输出、已知限制和用户需要执行的刷新动作。任何没有真实样本验证的功能不得写成“已支持”。
```

## D.15 AI 生成源的最终交付格式

AI 最终回复不应只发送一个 `.js` 文件。至少应包含以下内容：

| 交付物 | 内容 |
|---|---|
| 源文件 | 可导入的 Venera JavaScript，版本和 key 清晰 |
| 回归脚本 | 真实样本、请求桩、断言和可重复命令 |
| 专项日志 | 站点取证、路由、字段、图片协议、错误链和验证矩阵 |
| 主日志更新 | 新方法、新教训、可复用规则和限制 |
| 发布说明 | 改动、通过项、失败项、待验证项和用户操作 |
| 证据附件 | 关键 HTML/JSON/脚本/响应头/图片样本，按重要性排序 |

最终说明必须明确区分以下三种状态：

> **代码已实现**：源码中有对应分支，但不代表真实页面已经通过。
>
> **真实样本已通过**：使用保存的真实页面/响应完成断言，但不代表客户端所有缓存状态都已刷新。
>
> **客户端已确认**：用户或自动化客户端实际导入并点击验证通过，才可以写成稳定可用。

## D.16 本附录的核心结论

新 AI 生成 Venera 源效果不佳，通常不是因为缺少某个 CSS 选择器，而是因为跳过了证据矩阵、分类实现、章节详情契约、历史参数、图片协议判定、编译检查和真实回归中的一个或多个环节。今后评价一个新源，不能只问“有没有生成代码”，而要逐项检查“有没有真实取证、有没有完整功能链、有没有失败边界、有没有可复现测试、有没有客户端验收”。

因此，新源开发的最小不可省略集合是：**首页、搜索、分类、详情、章节、图片、封面、历史、权限、安全、编译、真实回归和日志交付**。任何缺少其中一项的源，都必须在发布说明中明确标记缺口。


## D.17 编译完成后的强制检验阶段

> **明确回答：有，而且从本版本起单独列为强制阶段。** 新源脚本通过 `node --check` 或等效编译检查，只能证明 JavaScript 语法可解析，不能证明 Venera 能加载、网页字段能解析、分类能工作、章节详情能打开或图片能加载。编译完成后必须继续执行本节的检验，未完成不得发布。

### D.17.1 编译后的固定执行顺序

```text
源脚本编写完成
    ↓
语法/编译检查
    ↓
Venera 兼容环境类加载与实例化
    ↓
元数据和返回类型检查
    ↓
真实 HTML/JSON 样本回归
    ↓
首页、搜索、分类、详情、章节、封面、历史专项断言
    ↓
安全拒绝和异常分支测试
    ↓
Venera 客户端实际导入与点击验证
    ↓
记录通过/失败/待验证并决定是否交付
```

任何一步失败，都必须停止“已完成”结论，记录失败输入和错误类型，修复后从编译检查重新开始。不能只修复测试失败的最后一个断言而跳过全链路回归。

### D.17.2 编译后检验清单

| 顺序 | 编译后必须检查 | 具体断言 | 不通过时的处理 |
|---|---|---|---|
| C1 | 类加载 | 源文件能被 Venera 兼容环境读取，类可以实例化 | 检查类名、继承、顶层语法和未定义变量 |
| C2 | 元数据 | `name`、`key`、`version`、`minAppVersion`、`url` 合法 | 修复元数据；非必要不改变已有 key |
| C3 | API 返回类型 | 首页 Comic、详情 ComicDetails、章节 Map、图片数组结构正确 | 检查构造器和空结构，不用普通对象替代合规类型 |
| C4 | 页面请求 | 实际请求 URL、编码、30x/Location、Referer 和 UA 正确 | 保存请求和响应，区分网络入口与解析问题 |
| C5 | 首页 | 至少一个真实区块和多个漫画卡片，ID/标题/封面非空 | 检查首页模板和懒加载字段 |
| C6 | 搜索 | 中文关键词有结果；无结果关键词安全返回；最终 URL正确 | 检查 action、重定向、编码和搜索专用选择器 |
| C7 | 分类 | 至少两个真实分类参数可返回漫画；第 2 页或终止页可解释 | 检查 categoryParams、分类 URL 和 maxPage 来源 |
| C8 | 详情 | 标题、可信封面、简介、标签和完整章节 Map 正常 | 检查详情 HTML、字段来源和章节容器 |
| C9 | 章节详情 | 最新、中间、较早三话均能打开并返回图片 | 检查章节 key、epId 标准化、整话/单页路由和权限 |
| C10 | 图片 | 封面、首图、尾图状态/文件头/尺寸可验证，数组去重 | 检查直链、懒加载、脚本、JSON 和加密判定 |
| C11 | 历史 | 纯 ID、完整 URL、文件名、组合 ID 和非法值按矩阵执行 | 修复 `loadEp` 标准化；非法值不得发畸形请求 |
| C12 | 安全 | 未知表达式、未知密钥、错误 Base64 或权限分支安全失败 | 禁止退回 `eval`、`Function` 或任意脚本执行 |
| C13 | 客户端 | 实际导入后搜索、分类、详情、章节图片可点击打开 | 记录 JS 引擎差异、缓存和客户端专属错误 |
| C14 | 交付 | 测试输出、证据、日志和限制说明齐全 | 缺一项就标记待交付，不发送“稳定版” |

### D.17.3 编译通过但功能失败时的判定规则

编译检查通过后如果首页为空，优先检查请求状态、重定向和页面选择器；如果搜索为空，优先检查最终搜索 URL、中文编码和结果容器；如果分类为空，优先检查分类参数与分页，不得只删除分类功能；如果详情页打不开，检查漫画 ID、详情 URL 和 HTML 响应；如果章节详情空图，检查章节 Map key、历史 `epId`、整话/单页路由和图片数据层次；如果图片参数错误，检查 Base64 padding、URL-safe 字符、权限和返回类型，不能直接更换为另一种加密算法。

# 附录 E：古风漫画（gfmh.app）源开发经验与可复用诊断规则

> 本附录将古风漫画（`gfmh.app`）案例中经过真实页面、原始 HTML、站点前端脚本、Venera 运行时桩和回归测试验证的经验，抽象为可迁移的开发方法。文中出现的站点 URL、选择器、漫画 ID、图片代理域名、AES Key 和图片数量均属于本案例事实，**不得未经重新取证复制到其他漫画源**。

## E.1 案例范围、版本和证据原则

古风漫画源的内部 Key 为 `GfmhApp`，用户可见名称为“古风漫画”，源 URL 为 `https://gfmh.app/`。本案例最终修复版为 v1.3.0。版本演进经历了三个具有明确边界的阶段：v1.1.0 修复阅读页动态 `params` 和章节 ID 标准化；v1.2.0 修复封面代理、搜索结果选择器和已删除详情页误解析；v1.3.0 补全 `ComicDetails` 的稳定字段，并确认一类表面上属于源错误、实际发生在 Venera 客户端已读状态逻辑中的空值异常。

本案例再次证明，错误日志本身也是站点取证材料。开发者不应只截取最后一行“无效参数”，而应同时保存请求 URL、请求头、HTTP 状态、响应正文片段、内联脚本变量、图片响应头、异常堆栈和前后章节链接。只有把这些内容按时间顺序关联起来，才能区分“源请求失败”“站点返回错误页”“图片 CDN 失败”和“客户端后置逻辑异常”。

| 证据层级 | 本案例实际材料 | 能证明的内容 |
|---|---|---|
| 站点页面 | 首页、搜索页、分类第 1/2 页、有效详情页、已删除详情页、多个章节页 | 路由、DOM、字段和错误边界 |
| 原始响应 | 保存的 gfmh HTML、章节 `params`、搜索结果和图片响应 | 可重复解析与回归 |
| 前端脚本 | `pic.js` 的 params 解密调用链 | AES-CBC、Key、IV 和明文 JSON 结构 |
| 客户端日志 | Venera `log.txt` | 实际请求顺序、网络错误和客户端堆栈 |
| 运行时桩 | 纯 ID、完整 URL、组合 ID、对象型章节输入 | 源 API 兼容性和图片数量 |
| 发布产物 | `gfmh.js`、开发日志、测试输出、ZIP、SHA-256 | 可导入、可审计和可复现交付 |

## E.2 页面必须按模板分别取证

古风漫画的首页、分类、搜索、详情和章节页使用了不同的 DOM 结构，不能把一个页面的列表选择器直接套到所有功能。首页的漫画区块使用 `.comic_box`，卡片是区块内的 `li`，封面/详情链接通常位于 `a.pic`，标题位于 `a.txt`，作者或副标题位于 `.author`。分类页使用 `.c_list .catagory-list > li`，封面链接可能是 `a.img.autoHeight`，标题仍可从 `a.txt` 获取，附加信息位于 `span.info`。源实现保留了 `a.pic`、`data-src`、`data-original` 等兼容分支，但这些分支都必须由同类页面的真实 HTML 证明。

搜索页不能复用首页和分类页的卡片容器。古风漫画的实际搜索请求为：

```text
GET https://gfmh.app/index.php/search?key={encodeURIComponent(keyword)}
```

真实搜索结果使用 `.u_list > li`。搜索单项的标题、详情链接、封面和作者字段与首页/分类并不完全相同，因此实现了独立的 `parseSearchItem`，并保留分页参数仅作为待持续验证的兼容路径。开发者应先保存至少一个真实关键词的搜索结果 HTML，再决定是否声明搜索已支持；不能因为搜索入口存在，就把首页卡片选择器当作搜索解析器。

详情页的主要容器是 `.infocomic .infobox`，标题为 `.infobox .title`，封面位于 `.infobox .info .img img`，作者和类型等元数据位于 `.infobox .info p.tage`，简介位于 `.infocomic .text`。章节列表使用 `.chapterbox .listbox ul.list li a`。在实时有效样本 `/388762.html` 中，章节 `/388762/111861.html` 的标题为“第1话3 觉醒的武魂”，前后章节分别是 `/388762/111860.html` 和 `/388762/111863.html`。[7] [8]

| 页面 | 真实路由/容器 | 本案例处理 | 维护要求 |
|---|---|---|---|
| 首页 | `/`、`.comic_box`、`li` | 解析多个区块和卡片 | 站点改版时单独重取首页样本 |
| 分类 | `/category`、`/category/list/{id}`、`.c_list .catagory-list > li` | 解析真实分页和分类列表 | 从页面分页节点确认 `maxPage` |
| 搜索 | `/index.php/search?key=...`、`.u_list > li` | 独立搜索解析器 | 不与首页/分类选择器混用 |
| 详情 | `/{comicId}.html`、`.infocomic .infobox` | 解析标题、封面、元数据和章节 Map | 检查 HTTP 200 下的错误正文 |
| 章节 | `/{comicId}/{chapterId}.html`、`#manga-imgs` | 先解析动态 params，失败再读静态图片 | 至少取首话、中间话和较新话 |

## E.3 HTTP 200 不等于详情有效

古风漫画对已删除详情页仍可能返回 HTTP 200。日志和实时响应均显示 `/388241.html` 返回正文“很遗憾，该漫画不存在或章节已被删除”，并附带跳转 `/category` 的脚本。若只检查 HTTP 状态，源会把错误页当作正常详情，继而在标题、封面或章节节点为空时产生二次异常。

因此，统一文档入口 `getDocument` 或详情加载逻辑必须同时检查状态码和错误正文。遇到“漫画不存在”“章节已被删除”等明确文本时，应安全抛出 `Comic not found`，而不是返回一个字段不完整的 `ComicDetails`。这类错误应在日志中标为**站点内容已删除**，不能误标为“章节协议失败”。

反过来，`/388762.html` 是有效详情页，且 `/388762/111861.html` 是有效章节；不能因为某个旧 ID 失效，就把同一站点全部详情都判定为不可用。有效与失效详情必须各保存一份，作为错误边界回归样本。

## E.4 封面 CDN 失败与图片正文失败必须分开处理

第二份 `log.txt` 中大量封面请求直接访问 `https://cover1.baozimh.org/...`，Venera 的 RHTTP 网络栈反复报告 `tls handshake eof` 或 `UnexpectedEof`。同一批封面经过站点可用的 `s2.325784.xyz` 代理后返回 HTTP 200、`content-type: image/webp`。这说明故障主要发生在封面 CDN/TLS 路径，而不是漫画详情 HTML 或正文图片协议。

本案例的封面处理流程是：先把封面转换为绝对 URL；仅当 URL 属于 `https://cover1.baozimh.org/` 时，使用 `Convert.encodeUtf8` 和 `Convert.encodeBase64` 编码完整原 URL，移除尾部 `=`，拼接为 `https://s2.325784.xyz/{base64}`；其他图片域名保持原 URL。代理转换失败时不猜测路径，而是回退原 URL并记录警告。

| 场景 | 正确判断 | 正确动作 |
|---|---|---|
| cover1 TLS EOF | 封面 CDN/TLS 路径不稳定 | 使用已验证的 s2 代理 |
| s2 返回 200/WebP | 代理路径可用 | 将代理 URL 写入 `Comic.cover` |
| 详情页返回错误正文 | 漫画/章节已删除 | 安全抛出 `Comic not found` |
| 章节 params 解密成功 | 阅读协议正常 | 继续生成正文图片 URL |
| 图片正文仍失败 | 需检查图片域名、Referer、状态和文件头 | 保存失败样本后再扩展协议 |

封面问题还会影响 Venera 历史记录，因为 `History.cover` 通常来自详情封面。修复源后，新打开的章节可能已经正常，但旧历史记录仍会保存旧的 cover1 URL 或默认图标。用户侧应使用客户端的“刷新信息/刷新历史”能力重新写入 `ComicDetails.cover`，不能把旧缓存继续显示误判为新源仍然失败。

## E.5 动态 params 的完整取证与安全实现

古风漫画章节页的静态 `#manga-imgs` 容器可以为空，真实图片列表位于内联脚本中的 `params` 字符串。阅读页还加载站点 `pic.js`，其中存在参数解密调用链。当前已验证的处理流程如下：

1. 用正则从内联脚本提取 `params` 字符串，不执行页面脚本。
2. 移除空白并补齐 Base64 Padding。
3. `Convert.decodeBase64` 得到二进制载荷。
4. 将前 16 字节作为 IV，将其余字节作为 AES-CBC 密文。
5. 使用 UTF-8 编码的已取证 Key `9S8$vJnU2ANeSRoF` 调用 `Convert.decryptAesCbc`。
6. UTF-8 解码明文，截取最外层 JSON，解析并校验 `host` 与 `images`。
7. 对每个图片值做绝对 URL 处理、协议校验和去重。
8. 任何 Base64、AES、UTF-8、JSON、host 或 images 校验失败，都返回安全的 `{ images: [] }`，不执行站点返回的 `eval`、`Function` 或任意 JavaScript。

本案例的明文至少包含 `host`、`images`、`source_id`、`comic_id` 和 `chapter_id`。已验证样本如下：

| 漫画/章节 | params 结果 | 图片数量 | 结论 |
|---|---|---:|---|
| `414201/149136` | host=`gfmh.app`、source_id=`10` | 70 | 通过 |
| `388695/122517` | host=`gfmh.app`、source_id=`10` | 143 | 通过 |
| `388762/111861` | host=`gfmh.app`、source_id=`10` | 8 | 通过 |

这里的 Key、IV 位置和 JSON 字段只对当前 gfmh 证据成立。不能因为另一个站点也有 `params` 字段，就直接套用 AES-CBC；必须重新获得密文、前端算法、Key/IV 来源和解密后有效图片四类证据。

> **安全规则：** 站点前端脚本是数据来源，不是授权执行代码。即使页面使用混淆、字符串表、动态变量或 `eval`，源也只能重放已取证的最小算法，不得把远程脚本直接交给 JavaScript 引擎执行。

## E.6 历史章节 ID 必须建立输入矩阵

Venera 不同入口可能向 `loadEp(comicId, epId)` 传入不同形态的章节参数。古风漫画源将下列输入统一为 `comicId|chapterId` 与真实章节 URL：

| 输入形态 | 示例 | 规范化结果 | 是否请求 |
|---|---|---|---|
| 普通章节 ID | `111861` | comic=`388762`、chapter=`111861` | 是 |
| 完整章节 URL | `https://gfmh.app/388762/111861.html` | `388762|111861` | 是 |
| 组合 ID | `388762|111861` | `388762|111861` | 是 |
| 带编码的 URL | `...%2F388762%2F111861.html` | 解码后再提取 | 是 |
| 对象参数 | `{epId: "111861"}`、`{chapterId: "111861"}`、`{url: ...}` | 读取白名单字段 | 是 |
| 漫画 ID 不一致 | `388695|111861` 用于 388762 | 无 | 否 |
| 缺失/未知参数 | 空值、无法识别的对象 | 无 | 否，返回空图片 |

解析器必须先校验嵌入 URL 的漫画 ID 与外层 `comicId` 一致，防止把历史记录中的旧源 ID 或组合参数错误拼接到新 URL。对非法参数安全返回空数组，比发出畸形请求或访问错误漫画更容易诊断。

章节 `onImageLoad` 也必须使用规范化后的章节 URL作为 Referer，而不能固定只使用首页 Referer。古风漫画日志中的正文图片请求均带有当前章节 Referer，例如 `https://gfmh.app/388762/111861.html`；因此章节详情、图片回调和历史章节输入必须作为同一条链路验证。

## E.7 Venera ComicDetails 的可选字段也要主动补全

Venera 类型定义允许 `ComicDetails` 的部分字段为空，但不同客户端版本和不同功能链路未必都以可空方式使用它们。古风漫画 v1.3.0 在详情返回中主动补全以下字段：

```javascript
new ComicDetails({
  title: title || comicId,
  subtitle: author,
  subTitle: author,
  cover: cover || "",
  description: description || "",
  tags,
  chapters,
  isFavorite: false,
  subId: comicId,
  thumbnails: cover ? [cover] : [],
  recommend: [],
  updateTime: updateTime || "",
  url: `${this.baseUrl}/${comicId}.html`,
});
```

这不是为了伪造站点数据，而是为了让源返回的对象在详情页、章节阅读、历史、收藏和缩略图链路中保持稳定字符串与数组类型。`subId` 使用漫画 ID 是本案例的兼容选择；如果站点有真实独立 UUID，应优先使用真实 UUID。

必须同时区分源侧兼容问题和客户端自身问题。古风漫画日志中，`/388762/111861.html` 的图片已经成功返回后，Venera 仍出现：

> `type 'Null' is not a subtype of type 'String'`  
> `LocalFavoritesManager.markAsRead` → `LocalFavoritesManager.onRead` → `_ReaderState.initState`

交叉读取 Venera 官方 `reader.dart` 和 `favorites.dart` 后确认，Reader 初始化后会调用 `LocalFavoritesManager().onRead(cid, type)`；客户端 `markAsRead(String id, ComicType type)` 会把 `appdata.settings['followUpdatesFolder']` 传给 `existsFolder(String name)`。当追更文件夹设置为 null 时，异常发生在客户端已读状态逻辑，而不是 gfmh 的 HTTP、params、章节 HTML 或图片返回。源端可以补全 `ComicDetails` 字段降低兼容风险，但不能从漫画源代码修改客户端的 `followUpdatesFolder` 设置。若相同堆栈仍出现，应在客户端关闭追更文件夹/阅读后移动收藏、重新初始化收藏设置或升级客户端。

## E.10 可复制的维护流程

当 gfmh.app 或任何其他站点改版时，应按以下顺序维护：首先复制当前源版本并保存新旧首页、搜索、分类、详情和章节响应；其次统计每类页面的节点数量，确认是页面改版、站点返回错误页还是网络/CDN 变化；再次比较 `params` 原始密文、Key/IV、JSON 字段和图片主机是否变化；然后只增加由新样本证明的解析分支；最后重新运行所有历史样本、至少三个不同时间/章节的动态协议样本、封面代理样本和错误页样本。

任何新增分支都应在开发日志中写清楚：原始证据路径、触发条件、输出结构、失败处理和回归结果。对动态响应，必须使用白名单解析；对站点返回的未知表达式、`eval`、`Function`、动态脚本或异常字段，默认安全失败并保存样本，不能为了让某一话显示图片而扩大执行权限。

## E.11 本案例最终经验

古风漫画案例把原日志中的通用原则进一步具体化为五条可复用经验。第一，**有效详情与有效章节必须用同一漫画的真实 ID 交叉验证**，不能拿已删除旧 ID 代表整站失败。第二，**封面 CDN 与正文图片协议必须分开排查**；封面 TLS EOF 可以通过已验证代理解决，但不能因此修改正文 params 解密。第三，**搜索页面必须建立独立解析器**，入口可用不等于结果选择器与首页相同。第四，**动态 params 必须以真实前端算法、密文、Key/IV、明文和图像响应构成完整证据链**，不能仅凭字符串长度猜测 AES。第五，**Venera 客户端堆栈必须按调用层级归因**；当异常发生在章节图片已成功返回之后，应优先检查客户端收藏/历史/追更后置逻辑，而不是继续修改站点解析器。

> **最终方法论：** 先保存成功与失败样本，再逐层定位“网络—页面—字段—协议—Venera 对象—客户端后置逻辑”的故障边界；每一次修复只改变有证据支持的最小部分；每一次发布都同时交付源文件、开发日志、回归脚本、原始证据和明确的客户端确认事项。

## G.2 加密取证（本案例核心，四证据规则落地）

章节页是 7.7KB 的壳，图片列表不在静态 DOM，而在加密变量：

```html
<script>var tpl_path='/template/pc/33/', params='{base64密文}';</script>
```

前端 `pic-v2.js`（jsjiami v7 混淆）+ `crypto-js.min.js` 解密 `params`。

| 证据 | 内容 |
|---|---|
| ① 密文来源 | 章节页内联脚本 `params` 变量（base64） |
| ② 算法调用链 | `params=decryptParams(params)` → `CryptoJS.AES.decrypt(...)`；图片走 `decryptImage` |
| ③ Key/IV | params key=`9S8$vJnU2ANeSRoF`（UTF-8），IV=base64 解码后前 16 字节；图片 key=iv=`my2ecret782ecret` |
| ④ 解密结果 | 复现得 `{host, source_id:15, comic_id, chapter_id, images:[...]}` |

**params 解密流程**：base64 → 前 16 字节 IV → AES-128-CBC(Pkcs7) → UTF-8 → 截取最外层 JSON。

**图片层次**：`source_id==15` 直链（`dmw.546457.xyz/*.webp`，需 Referer）；`source_id==12` 图片响应本身 AES-CBC 加密（key=iv=`my2ecret782ecret`，未遇样本，待验证）。

> **取证方法（新增，关键）**：混淆脚本不是用来手推的，而是**运行它 + 拦截 `CryptoJS.AES.decrypt`** 直接拿到真实 key/iv。用 node + vm 沙箱加载 `pic-v2.js`，给 `$`/`window`/`document`/`params` 打桩，monkey-patch `CryptoJS.AES.decrypt` 记录 key/iv，即可复现并提取密钥。

> **规则（新增）**：`manwang` 的 params key `9S8$vJnU2ANeSRoF` 与古风漫画（gfmh.app）案例相同——同一平台后端共享密钥。但每站仍需在前端重新取证确认，不能直接套用。

**排查链路与逐层排除**：

本次修复针对用户反馈的两个问题：首页只有少量固定卡片、搜索不可用。实现前重新核对了 [漫网首页](https://www.manwang.net/)、[最新更新](https://www.manwang.net/custom/update)、[人气排行](https://www.manwang.net/custom/hot)、[连载列表](https://www.manwang.net/category/finish/1)、[完结列表](https://www.manwang.net/category/finish/2) 和 [分类页](https://www.manwang.net/category)，并将 HTML 保存在 `manwang_debug/responses*.html` 与 `/home/ubuntu/upload/www.manwang.net__1787719267969.html`，没有凭页面名称猜测选择器或路由。

#### G.6.1 首页问题：不是“不能滑动”，而是原实现只返回了首页首层少量卡片

原 v1.0.4 只读取首页两个 `.panel-comic` 的右侧 `.item-comic`，每区约 6 项，忽略了轮播和左侧 `.panel-comic-l` 重点推荐，也没有使用导航中已经存在的独立列表页。因此 Venera 虽然采用了 `singlePageWithMultiPart`，返回内容仍然很少，用户会感觉首页不能继续浏览。

v1.1.0 保留首页真实结构并增加独立分区：`#slider .slides li` 作为“轮播推荐”；每个 `.panel-comic` 同时解析左侧重点推荐和右侧普通卡片；再请求站点导航真实指向的 `/custom/update`、`/custom/hot`、`/category/finish/1`、`/category/finish/2`，分别显示为“最新更新”“人气排行”“连载漫画”“完结漫画”。本地真实样本回归共得到 **103 部去重漫画**，其中最新更新和人气排行均为 30 项，连载为 16 项，完结为 10 项。这里使用多个真实分区，而不是伪造 `loadNext` 或无限递增页码；每个分区请求失败时只丢弃该分区，不影响其他已经成功的内容。

#### G.6.2 搜索问题：官方搜索入口正确，但当前出口返回空结果或限流

表单证据仍是 `action="/index.php/search"`、字段 `name="key"`，所以源首先请求 `GET /index.php/search?key={encodeURIComponent(keyword)}`。对“妖神记”“斗罗大陆”等关键词，当前沙盒和用户浏览器均观察到两类真实响应：HTML 空壳并显示“搜索结果（0）”，或 JSON `{"msg":"搜索繁忙","code":-1}`。此前已对路径式 `/search/{kw}`、POST、旧版 `/api/front/index/search` 等变体取证，未找到当前网络下能稳定返回真实结果的备用入口。开发日志 G.3 的跨出口实测还显示，该站搜索存在客户端 IP/地区差异；因此不能把“换选择器”或“补 Cookie”写成已经恢复全球搜索。

v1.1.0 的处理顺序是“官方入口优先，真实站内目录有限兜底”：第一步仍调用官方搜索；当响应为空、限流、失败或解析不到 `.comic-item` 时，只对已实际抓取的首页、更新、排行、连载、完结和分类第一页进行标题、副标题、简介过滤，并使用 `searchCatalogCache` 避免同一源会话反复下载目录。这样“鬼灭之刃”等当前已出现在真实列表中的标题可以得到可用结果，且封面继续来自真实卡片 URL。由于没有取证到全站搜索结果分页，v1.1.0 对搜索第 2 页安全返回空结果并标记 `maxPage=1`，绝不伪造总页数。

> **边界必须保留：** 该兜底是“已取证站内目录的本地过滤”，不是全站搜索索引，也不能绕过网站按 IP/地区返回空结果的服务端限制。若目标漫画不在已取证目录中，或用户的网络出口仍使官方搜索返回 0，源无法仅靠 JavaScript 保证全局搜索；发布说明应明确提示用户检查客户端网络出口，并反馈未命中的标题以便追加真实目录样本。

### G.9 搜索规则最终判定：请求格式正确不等于服务器索引可用

本轮专门按“网站搜索规则”重新验证，而不是继续增加猜测参数。真实搜索页源码明确给出 `<form action="/index.php/search">`、默认 GET 方法、`<input name="key">` 和提交按钮；因此规范请求就是 `GET /index.php/search?key={encodeURIComponent(keyword)}`。页面本身没有隐藏 token、签名字段或必须由前端计算的参数。用户浏览器直接访问“妖神记”“元尊”和“古见同学有交流障碍症”时，页面标题会带入关键词，但结果区分别显示对应的“搜索结果（0）”，同时保留静态“大家都在搜”链接。

当前首页 `index.js` 的搜索相关代码只在点击 `#search-input` 时展开 `.layer-search-all`，没有输入联想请求。详情页遗留的 `base.js` 虽然包含 `POST /api/front/index/search`，但使用正确 `key` 参数、AJAX 请求头和 Referer 重放仍为 HTTP 404；搜索页实际也不加载该脚本。因此，`/api/front/index/search` 不是当前可用的搜索规则。

多关键词实验还显示服务端存在动态保护状态。未触发保护时，不同请求有过偶发不同响应；连续进行桌面/移动 User-Agent、参数顺序、分页和 POST 对照后，当前出口大量请求统一变为 HTTP 403 保护页，隐藏 API 仍为 404。由于这种偶发响应不能稳定复现，不能把某一个 User-Agent、分页参数或请求头宣称为修复规则。用户真实浏览器对同一站点搜索也持续得到 0 结果，进一步排除了“Venera 选择器写错”这一单一原因。

| 搜索规则层 | 已确认事实 | 源代码能否解决 |
|---|---|---|
| 表单格式 | GET `/index.php/search?key=关键词` | 能，v1.1.0 起已按此实现 |
| 页面解析 | 有结果时应解析真实 `.comic-item`；当前样本为空 | 能，解析器已支持 |
| 隐藏 AJAX | `/api/front/index/search` 当前 HTTP 404 | 不能靠改参数恢复不存在的路由 |

| 网络保护 | 重复探针可触发 403；部分请求返回“搜索繁忙” | 只能减少请求并安全回退，不能保证绕过 |
| 本地补救 | 真实分类分页可扫描并按标题过滤 | 能；v1.1.1 已实现并缓存 |

**最终判定：** 通过查询网站搜索规则可以确认源的官方请求写法没有根本错误，但不能仅凭这个规则彻底恢复漫网当前不可用的全站搜索。v1.1.1 的正确策略是官方入口优先，失败后只使用漫网自身真实分类/推荐卡片过滤；“妖神记”和用户输入的“妖神计”可以命中真实 `/book/503735`。对古见作品，因为全分类和相关题材分页都没有提供漫网详情 ID，继续猜测 ID 或调用第三方搜索都会制造虚假结果。

# 附录 F/G：跨案例新增可复用规则（写入主日志）

## 1. 图片「签名 URL」≠「加密」
URL 里带 `key`/`sign`（32 位 hex 等）通常是**服务端签名**，直接提取即可；只有当「响应体/图片字节需要客户端解密」时才走 AES/RSA。判定依据：下载一张图看文件头（`ff d8`=JPEG、`RIFF`=WebP）——是标准图片头就说明没加密。

## 2. 加密确认的「四证据规则」落地方法
对动态加密（如 params 密文）：
1. 密文来源（内联 `<script>` 变量 / JSON 字段）；
2. 算法调用链（前端 `CryptoJS.AES.decrypt` 等）；
3. Key/IV 来源（硬编码字符串 / 派生）；
4. 解密成功结果（合法 JSON / 真实图片）。
**取证技巧**：运行混淆脚本 + 拦截解密函数拿真实 key/iv，不手推混淆字符串。

## 3. 图片反盗链用 Referer
正文图常「无 Referer 403、带站点/章节 Referer 200」。`onImageLoad(url, comicId, epId)` 返回 `{headers:{Referer: 章节页URL}}`；注意用规范化后的章节 URL 作 Referer。

## 4. Accept-Encoding 对加载速度是量级影响
强制 `Accept-Encoding: identity` 会让大页面不压缩传输（实测详情页 363KB vs gzip 7KB，约 50 倍）。**正确做法：不设置该头，交给引擎默认处理**——服务端在无 Accept-Encoding 时通常返回明文（安全），引擎支持 gzip 时则自动压缩（快）。已应用 tuku.cc 与 manwang 两个源。

## 5. 搜索「空结果」≠ 反爬，先排除「IP/地区限制」
搜索返回「搜索结果（0）」时，不要立刻断定反爬指纹或 Cookie 缺失。**决定性验证：用真实（无头）浏览器从目标网络请求一次**——
- 若浏览器也从你的 IP 得到空结果、而用户在另一网络（如国内）有结果 → 是 **IP/地区限制**，源无法修复，提示用户检查客户端代理/网络出口；
- 若浏览器有结果而脚本没有 → 才考虑 cookie/指纹/JS 渲染。

## 6. 无头浏览器是决定性验证工具
当「浏览器行为无法用脚本复现」时，用无头浏览器（puppeteer-core + 系统 Edge/Chrome）实测：能拿到挑战 cookie、看到服务端返回的真实 HTML/结果，从而区分「IP 限制 / Cookie / JS 渲染 / 反爬指纹」。

## 7. 环境/沙箱限制备忘（开发工具层面）
- Windows 沙箱下 `curl` 的 schannel 后端可能报 `SEC_E_NO_CREDENTIALS`，改用 **node fetch**。
- PowerShell 5.1 无 `-SkipHttpErrorCheck`、无三元运算符 `? :`，脚本里用 if/else 与 try/catch 替代。
- 沙箱禁止子进程管道捕获（`spawn EPERM`）：启动外部程序用 `stdio:'ignore'`，或用 CDP/HTTP 连接替代管道。
- 无头 Edge 需 `--remote-allow-origins=*` 才允许 puppeteer 连接；`--single-process/--no-zygote` 易崩溃，用最小参数 `--headless --no-sandbox --disable-gpu` 更稳。

# G.11 爱看漫 v1.1.0：首页扩展与抗小改动稳定性

## G.11.1 首页问题与包子漫画对照

爱看漫旧源的探索页只请求首页并固定读取“本周推荐”和“今日更新”，站点首页一旦只有少量卡片，Venera 就只显示一页内容。对照 Venera 官方包子漫画源可知，稳定的首页不应把分区数量写死在一个数组里，而应在一次真实首页响应中遍历可识别的分区容器；包子源使用 `singlePageWithMultiPart`，每个非空容器独立生成一个标题和漫画列表。该设计依据官方源和官方文档，不是凭空猜测。

新旧日志表明，爱看漫当时的主要故障包括 `chapterlink` connection closed、首页 UnexpectedEof、详情 ConnectionReset、收藏页 BrokenPipe 和 CDN/接口连接关闭。稳定性问题不只在图片选择器，也在请求链：未登录详情页每次先访问 `/user/bookcase`，然后把 `/api/comic/zyz/chapterlink` 当成章节列表硬前提。v1.1.0 延续并强化前一版修复，取消详情页收藏预请求，详情 HTML 的真实章节链接先入列表，chapterlink 只作为补充；站内 HTTP 章节链接统一升级 HTTPS。

## G.11.4 维护原则

首页增加内容应优先使用已经真实取证的同源分区，而不是猜测新的 API；请求数量要在代码中可数，并让每个分区独立失败。详情和章节应设计成“HTML 真实数据优先、动态接口可选补充”；图片应设计成“真实候选优先、响应文件头先验、错误页不进阅读器”。网站返回 403、404、BrokenPipe、ConnectionReset、UnexpectedEof 或 connection closed 时，必须先归类为访问/连接问题，不能立即重写图片规则。只有重新取得当前页面、API 原始响应和图片文件头后，才允许更新参数、CDN 或解密逻辑。

# G.13 爱看漫 v1.1.2：统一网络容错、章节 ID 契约与分页完整性

## G.13.1 生成前的域名证据门槛

本轮没有因为旧源的搜索失败就猜测新的搜索参数。用户浏览器当前访问 `https://www.ikmmh.com/` 和 `/search?searchkey=古见同学` 都返回 404，而旧 `log02` 曾记录同一 www 首页返回 200；公开源请求记录也显示爱看漫存在地区和线路差异。由此形成新的规则：**当前首页或搜索表单没有取得有效 200 HTML 时，不得凭空增加备用域名、`search.html` 或新 API 参数。** 多域名设置只有在每个域名都经过首页、详情、章节和图片 CDN 验证后才可以加入。

## G.13.2 v1.1.2 稳定性改造

v1.1.2 将 GET 和只读 POST 统一到有限请求重试层。`UnexpectedEof`、timeout、connection reset、closed connection、broken pipe 和 5xx 最多重试一次并等待 250 毫秒；403、404、`The region has been denied`、明确参数错误不会进入普通网络重试。这样既覆盖 log02 的瞬时断线，又避免把站点拒绝放大成高频流量。

`read/pics` 继续遵循已取证的 `data.pic[].pic`，但分页推进改用服务器返回的 `offset/limit/total`。源会检测异常 offset、连续重复分页、分页不推进、提前结束和安全上限；若累计数量不足服务端 total，不把结果当作完整章节。`read/index` 改为只遍历 `pic/pics/images/list/items/data/result` 等已知图片容器和 `pic/url/src/image` 等图片字段，不再递归扫描全部 JSON 字符串，减少封面、推荐图、头像和错误页混入正文的可能。

## G.13.3 Venera 数据契约和图片回调

Venera 官方契约将 `ComicDetails.chapters` 定义为 chapter id 到 title 的 Map。因此 v1.1.2 使用稳定 cid 作为章节 Map key，并让 `loadEp`、`onImageLoad` 同时接受完整 URL和数字 cid；数字 cid 按已经取得证据的 `/chapter/{aid}/{cid}.html` 路由解析。该改动需要实机继续验证历史、缓存和上一章/下一章跳转，不能把桩测试当成全部 App 验证。

单个真实正文图片最多执行一次同 URL 的 `onLoadFailed` 回退，以覆盖 log02 中 CDN 先 timeout、随后同 URL 返回 200 的情形；第二次失败立即停止，不生成猜测地址。登录用户名和密码增加 URL 编码，分类重复标签删除，登录、分类、搜索、收藏、详情和章节错误统一保留底层错误内容。

## G.13.4 验证重点与未验证边界

**验证是发布重点。** v1.1.2 已通过 `node --check` 与 Venera 兼容回归。新增测试覆盖瞬态 GET 重试、403 不重试、数字 cid、章节 Map key、严格 API 图片字段、log02 的 28 张 `data.pic` 三页分页、首个 `UnexpectedEof` 后恢复、分页完整性、单图一次回退、首页/详情降级、短章节、UUID、无效参数和错误图片响应。最终输出为：`PASS ikmmh v1.1.2: request retry, cid contract, strict API fields and log02 pagination assertions passed`。

当前沙盒对爱看漫 API 仍可能收到地区拒绝，用户浏览器当前首页/旧搜索路由也为 404。因此本版本不能宣称当前线路已经完整在线阅读；后续若要修复搜索或新增线路，必须先取得当前有效首页、搜索表单、至少一个正确结果、第二页或 next token、详情章节和正文图片的完整证据。

# G.14 MOJOIN（mojoin.com）新源开发记录：API 直取与双层 AES-CBC 图片解密

## G.14.1 本期目标与取证原则

本期新增站点为 MOJOIN：`https://mojoin.com/`。按照本日志要求，先对首页、列表、类型、详情、章节列表、单章接口和正文图片进行真实取证，再开始编写 Venera 源。没有执行远程站点 JavaScript，也没有把搜索摘要、第三方镜像或未知图片目录当作协议证据。

## G.14.2 MOJOIN API 事实清单

MOJOIN 漫画后端 API 主机为 `https://mojoin-api.com/comics`。访客 API 请求由当前前端代码使用 `device: web` 和 `uuid` 头；前端提供访客 UUID 获取逻辑，源中保留真实默认 UUID 作为失败时的继续工作路径。

| 功能 | 真实接口 | 取证结果 |
|---|---|---|
| 首页更新 | `/book?page=1&rows_per_page=20&order_by=updated_at:desc` | `code=0`，样本 `total=220`、`last_page=11` |
| 类型列表 | `/book/type` | 49 个类型项，字段含 `id/name/nickname` |
| 分类列表 | `/book?page=1&rows_per_page=20&type=1` | `code=0`，样本 `total=38`、`last_page=2` |
| 搜索 | `/search/page?keyword=Nine%20Sols&page=1&rows_per_page=20&subtype=1` | 返回 2 个结果，`subtype=1` 为漫画 |
| 作品详情 | `/book/info/224` | 返回标题、封面、作者、简介、类型、状态等字段 |
| 章节列表 | `/book/224/chapter` | 3 章；数据库 id 为 4045/4083/4096，公开编号为 001/002/003 |
| 单章内容 | `/book/224/chapter/001` | 返回 21 个 `content` 项，每项含 `url/key/width/height/filename` |

MOJOIN 阅读页真实路由是 `/comics/{bookId}/{customizedNumber}`，例如 `/comics/224/001`。因此 Venera 章节 Map 应使用 `customized_number`，而不是直接使用数据库 chapter id；`loadEp` 按公开编号请求单章接口。

## G.14.3 正文图片不是直链：真实双层解密规则

单章 API 中的正文 URL 形如：

```text
https://mojoin-api.com/comics/fs/chapter_image/{content-uuid}/content/page/standard_0
```

直接重放第一张图得到 HTTP 200，但响应是 `application/octet-stream`，长度 85776 bytes，文件头为 `c0 7b e9...`，不是 JPEG。每一个正文内容项同时有一个 `key`。这一步排除了“直接返回 url 即可显示”的实现方式。

继续静态分析 MOJOIN 当前的 `ImageDecode-ZlwNcRZo.js` 和 `worker/AESDecrypt.js`，取得真实前端调用：

```text
ImageDecode.decode(token, content.key, content.url)
```

其中访客阅读 token 为 `freereadingcomicstar`。算法分两层：首先计算 `SHA-512(token)` 的小写十六进制结果，取前 64 个 hex 字符作为外层 AES-256 key，取索引 30 到 62 的 32 个 hex 字符作为外层 AES-CBC IV，用 AES-CBC/PKCS7 解密 `content.key` 的 base64 字符串，得到 `imageKeyHex:imageIvHex`。然后读取正文 URL 的密文二进制并转成 base64，以第二阶段 key/iv 再次 AES-CBC/PKCS7 解密，得到 `data:image/jpeg;base64,...`，最后将 base64 还原成图片二进制。

真实样本复现结果如下：

| 阶段 | 结果 |
|---|---|
| `content.key` 解包 | `614bb0c26e17f77db83a3eac57a7325bc36ac62fe5c570cacd84298d71f6e0d5:5bc36ac62fe5c570cacd84298d71f6e0` |
| 正文密文响应 | HTTP 200，85776 bytes，`application/octet-stream` |
| 解密后 MIME | `image/jpeg` |
| 解密后长度 | 64311 bytes |
| 文件头 | `ff d8 ff e0 00 10 4a 46 49 46` |

结论是：MOJOIN 的正文图片保护属于“API 返回 key + 图片二进制密文 + 双层 AES-CBC/PKCS7”组合。不能把密文 URL 交给 Venera，也不能从封面猜测图片目录。

## G.14.4 v1.0.0 源实现和稳定性设计

MOJOIN v1.0.0 的首页、搜索和分类均使用实测 API，并使用服务器返回的 `last_page` 作为 Venera `maxPage`。类型列表依据真实 `/book/type` 结果整理，按 nickname 或显示名称去重，避免站点重复类型造成重复分类。

作品详情请求 `/book/info/{id}` 和 `/book/{id}/chapter`，章节 Map 使用 `customized_number`。`loadEp` 兼容纯 bookId/章节编号、完整作品 URL和完整阅读 URL，严格要求单章内容中的 URL 匹配官方 `chapter_image` 路径，并要求同一项存在 key。

源将每个正文 URL 和对应 key 编码为内部标记；图片加载时恢复真实 URL，在 `onResponse` 中使用 Venera `Convert.sha512`、`Convert.hexEncode`、`Convert.decryptAesCbc`、`Convert.decodeUtf8` 和 `Convert.decodeBase64` 完成解密，返回 Venera 需要的 ArrayBuffer。这样没有执行网页脚本，也没有把未知字段或任意字符串当作图片。

网络层最多对瞬态连接错误和 5xx 重试一次，不对 401、403、404、权限限制和错误参数无限重试。图片层最多进行一次同 URL 重试。解密失败、空章节、锁定章节或 `can_view=0` 时直接报告明确错误，不伪造正文图。

## G.14.6 本期可复用经验

第一，API 返回 HTTP 200 并不代表图片已经是明文图片；必须同时检查 Content-Type、文件头和解码结果。第二，网页阅读页可以提供最可靠的解密调用链，优先追踪其 `ImageDecode` 和 worker，而不是猜测 AES 密钥或从变量名提取字符串。第三，当章节公开路由使用自定义编号时，Venera 章节 key 要与公开阅读编号一致，并让 `loadEp` 兼容历史和完整 URL 输入。第四，图片源内部状态不能把密钥拼进最终 URL 直接交给阅读器，必须在 `onResponse` 中解密后返回二进制。第五，站点的 401、403、锁定章节、地区限制和网络 timeout 必须分层记录，不能全部显示成“无效参数”或“找不到图片”。

# G.15 MOJOIN 导入失败修复：回到 Venera 原始编译规则

## G.15.1 导入失败的排查方法

MOJOIN v1.0.0 的 Node 语法检查和功能 fixture 回归均通过，但用户反馈实际 Venera 无法导入。因此本轮没有把“语法检查通过”当成导入成功，而是直接对照 `ComicSourceParser.parse`：导入器会寻找第一个以 `class ` 开头且包含 `extends ComicSource` 的类，把整个文件包装在闭包中执行，实例化该类，读取 `name/key/version/minAppVersion`，再由导入器写入 `ComicSource.sources.{key}`。[1]

这说明源文件末尾不应自行 `new` 或手动注册，key 必须满足字母、数字和下划线规则且不能与已安装源重复。用户没有提供弹窗原文，所以不能把 v1.0.0 的实际阻断点武断归结为某一条；需要同时检查 key 重复、最低版本门槛、类名识别、现代语法和元数据缺失。

## G.15.2 v1.0.1 兼容重写

MOJOIN v1.0.1 新建为独立文件，不覆盖 v1.0.0。文件顶层只保留注释和一个 `class MojoinV2 extends ComicSource`，所有辅助函数改为类方法或类字段，去除对象展开、可选链和空值合并写法，文件末尾只结束类定义。

为规避用户设备已经保存旧版 `mojoin` 时的重复 key，v1.0.1 使用 `mojoin_v2`；版本改为 `1.0.1`。同时不声明 `minAppVersion`，避免较旧客户端在导入阶段因版本门槛直接拒绝；支持 `onLoadFailed` 的客户端仍会使用一次有界图片重试，旧客户端至少可执行 URL、请求头和 `onResponse` 解密流程。

搜索和分类选项也按 Venera parser 的实际形态处理：parser 将选项数组传给 `search.load(keyword, options, page)` 和 `categoryComics.load(category, param, options, page)`，源读取数组中的 API key，而不是把中文显示文本发送给 MOJOIN。

## G.15.3 导入结构与功能验证

本轮创建了与 Venera parser 同形态的闭包导入包装：执行 `(() => { 源代码; this['temp'] = new MojoinV2() }).call()`，读取实例元数据并写入模拟 `ComicSource.sources`。结果如下：

```text

PASS MOJOIN v1.0.1: 7 mocked requests, strict parser wrapper, 21 encrypted pages, AES-CBC image decode and route contracts passed
```

除了导入包装，还重新执行了 `node --check`、首页、搜索、分类、详情、章节、完整 URL 入参、21 页密文正文、双层 AES-CBC 图片解密、JPEG 文件头和一次图片失败回退测试。

> **重点：本地导入包装通过只能证明文件符合 parser 的结构和 JavaScript 运行环境；如果用户导入 v1.0.1 仍失败，必须取得 Venera 弹出的完整错误文本，才能区分 `key already exists`、`Invalid Content`、版本门槛、语法错误或客户端运行时差异。**

# G.16 MOJOIN v1.0.2：`FormatException: Invalid number` 导入错误修复

## G.16.1 用户真实错误

用户提供了 Venera 导入截图，原文为：

```text
FormatException: Invalid number (at character 1)
^
```

这次错误发生在源导入阶段，不是 MOJOIN API、章节正文或图片解密阶段。

## G.16.2 真实根因

Venera `ComicSourceParser.parse` 实例化源后会读取 `minAppVersion`。如果该字段不是 null，就进入 `compareSemVer`；该函数把版本按点号分割，并对前三段执行 `int.parse`。[1]

MOJOIN v1.0.1 为了避免旧版客户端最低版本门槛，省略了 `minAppVersion`。但 Venera 基础 `ComicSource` 类本身把它初始化为空字符串 `""`，因此 parser 读取到的不是 null，而是空字符串，最终对第一段空值执行数字转换，产生 `FormatException: Invalid number (at character 1)`。

这纠正了 v1.0.1 中“省略 minAppVersion 可以提升旧版兼容性”的错误判断。对于 Venera 源，若基础类提供了空字符串默认值，必须显式覆盖为合法三段式数字版本。

## G.16.3 v1.0.2 修复

v1.0.2 明确写入：

```javascript
class MojoinV2 extends ComicSource {
  name = "MOJOIN";
  key = "mojoin_v2";
  version = "1.0.2";
  minAppVersion = "1.0.0";
  url = "";
}
```

其余 MOJOIN API、章节 `customized_number`、访客 UUID、双层 AES-CBC 图片解密和一次有界图片重试均保持不变。源文件仍只有一个 `class ... extends ComicSource`，不手动实例化或注册。

## G.16.4 验证重点

本轮导入包装测试不仅实例化 `MojoinV2`，还模拟 Venera 对 `minAppVersion` 的前三段数字解析。最终输出为：

```text
PASS import wrapper: MOJOIN mojoin_v2 1.0.2; source registered
PASS MOJOIN v1.0.2: 7 mocked requests, valid version metadata, 21 encrypted pages, AES-CBC image decode and route contracts passed
```

同时通过 `node --check`、真实 API fixture、详情、章节、21 页图片解密、JPEG 文件头和一次图片失败回退测试。

> **重点：`node --check` 只验证 JavaScript 语法；Venera 导入还必须验证元数据默认值、`minAppVersion`、key 注册和 parser 的版本比较。以后所有新源都必须显式设置合法的 `minAppVersion`，不得依赖基础类空字符串默认值。**

# G.17 MOJOIN v1.0.4：章节详情成功但正文图片为空

## G.17.1 log.txt 的真实故障链

本次日志同时包含 MOJOIN API 瞬态网络错误和 Venera 本地历史记录异常。作品 257 的详情接口与章节列表接口均返回 200，作品 261 的详情接口在第一次 `UnexpectedEof` 后重试并返回 200，说明章节详情链路基本可达。

但打开阅读器后，作品 257 的单章 `/book/257/chapter/00_SP` 和作品 261 的单章 `/book/261/chapter/001` 曾出现 timeout、`peer closed connection without sending TLS close_notify` 和 Windows `ConnectionAborted`。此时多数请求还没有进入正文图片 URL 阶段，日志中没有 `chapter_image` 图片请求，也没有 `onResponse` 或 AES 解密堆栈。

另外，日志中的 `type 'Null' is not a subtype of type 'String'` 位于 `LocalFavoritesManager.markAsRead`，以及早先的 `HistoryImageProvider`、`ComicType.sourceKey` 空值错误，属于 Venera 历史/收藏层，不能当作 MOJOIN 图片协议错误。

## G.17.2 发现的源代码缺陷

对 log.txt 中实际取得的单章 JSON 进行摘要后发现，作品 257 的 `00_SP` 返回 56 个 `content` 项，作品 261 的 `001` 返回 135 个 `content` 项。每项包含 `url`、`key`、`filename`、`width` 和 `height`，但真实正文路径为：

```text

```

v1.0.3 的 `isMojoinChapterImage` 只接受 `/content/page/...`，因此单章请求一旦成功，源仍会把所有 `/content/roll/...` 项过滤掉，最后返回“没有正文图片”。这才是章节详情能打开但正文图片列表为空的确定源缺陷。

## G.17.3 v1.0.4 修复

v1.0.4 将正文白名单扩展为仅接受官方 `chapter_image/{UUID}/content/page/{name}` 和 `chapter_image/{UUID}/content/roll/{name}` 两类路径，不接受任意主机或任意字符串。同时把单章接口的瞬态错误重试从最多两次提高为最多三次，覆盖 log.txt 中 timeout、ConnectionAborted 和 UnexpectedEof 后恢复的情形；403、404、权限错误和明确参数错误不重试。

双层 AES-CBC 解密逻辑没有被猜测性修改。低频重放两个真实图片 URL 均返回 200 `application/octet-stream`，v1.0.4 的 `onResponse` 解密结果均为合法 JPEG：

```text

261_001: encrypted=177296 decoded=132944 signature=ffd8ffe000104a4649460001
```

# G.18 MOJOIN v1.0.5：Base64 外层密钥与 Venera CBC padding 导致的无效十六进制

## G.18.1 问题边界和用户判断核对

本轮最高优先级证据是用户最新 `log.txt`。日志已经显示 v1.0.4 成功读取真实单章 JSON，发出 `chapter_image/.../content/roll/standard_N` 正文请求，并收到 HTTP 200、`application/octet-stream`；之后才在 `decryptImageResponse -> hexToArrayBuffer` 报“MOJOIN 解密 key/iv 不是有效十六进制”。因此本轮不再修改已验证的章节路径、`content[]` 白名单或 API 参数，问题边界确定为图片响应解密内部。

用户关于“图片 key 不是十六进制”的观察需要分层解释：MOJOIN `content[].key` 的确不是 hex，而是 152 字符左右的 Base64 外层密文，常含 `/`、`+`、`=`。但 v1.0.4 已执行 `Convert.decodeBase64`，所以不能把“原始 content.key 不是 hex”直接当作 v1.0.4 当前报错的最终原因。只有外层 AES 解密并去 padding 后得到的第二层 `key:iv` 文本，才应该分别是 64 个和 32 个 hex 字符。

## G.18.2 Venera AES-CBC 行为的源码证据

Venera 官方 Javascript API 将 `Convert.decryptAesCbc` 定义为接收和返回 `ArrayBuffer`。[1] 官方 Dart 的 `js_engine.dart` 在 `aes-cbc` 分支中使用 PointyCastle `CBCBlockCipher(AESEngine())`，循环执行 `processBlock` 后直接返回等长结果，没有使用 `PaddedBlockCipher`，也没有自动移除 PKCS#7。[2] 这与 Node `crypto.createDecipheriv` 默认自动去 padding 的测试行为不同。

因此，前一版使用 Node 默认自动去 padding 的回归只能证明 AES 参数和密文匹配，不能充分模拟 Venera 的 `Convert.decryptAesCbc`。本轮将所有 v1.0.5 回归桩改为关闭 Node 自动 padding，并由源代码显式严格校验/去除 PKCS#7。

## G.18.3 最新真实密文的逐层证据

使用 log.txt 对应的 book 256/chapter 002 完整 JSON 和 `standard_2` 正文密文进行逐层解密，证据如下：

| 层级 | 原始结果 | 去 padding 后结果 |
|---|---:|---|
| `content.key` Base64 解码后的外层密文 | 112 bytes | — |
| 外层 AES-CBC 明文 | 112 bytes，末尾 15 bytes 全为 `0x0f` | 64-hex key + `:` + 32-hex iv |
| `standard_2` 图片密文 | 141520 bytes | — |
| 图片 AES-CBC 明文 | 141520 bytes，末字节为 `0x01` | `data:image/jpeg;base64,...` |
| 最终图片 | — | 106120 bytes，JPEG/JFIF，960×1920 |

去 padding 后的真实第二层密钥文本为：

```text
7fb0f7a094ea3a8c871c166d73ba174e76c5688af578fbb6e9a4fad3a5f56c18:4e76c5688af578fbb6e9a4fad3a5f56c
```

最终 JPEG 文件头为：

```text
ff d8 ff e0 00 10 4a 46 49 46 00 01
```

这直接证明 v1.0.4 报错的确定原因是：外层 CBC 明文的 PKCS#7 尾部没有被清除，控制字节混入 `parts[1]`，再被 `hexToArrayBuffer` 判定为非纯 hex；不是站点返回了错误的第二层 key/iv，也不是正文 URL 失效。

## G.18.4 v1.0.5 最小修复

v1.0.5 新增 `unpadPkcs7(value)`，检查输入非空、末字节范围 1–16、padding 长度不超过明文长度以及所有尾部字节一致。外层 `content.key` 先 Base64 解码、AES-CBC 解密、去 padding，再 UTF-8 解码和拆分 `key:iv`；第二层正文也先 AES-CBC 解密、去 padding，再解析 data URI 并 Base64 还原为 ArrayBuffer。

本轮没有覆盖 v1.0.4 文件，没有改变源 key `mojoin_v2`、`minAppVersion=1.0.0`、`page/roll` 官方路径白名单、访客 UUID、`device: web`、Origin/Referer、章节 `customized_number` 或有限网络重试。这样可以把修复范围限制在已经由真实日志定位的解密输出处理。

## G.18.5 **强制验证结果**

以下验证均在独立 v1.0.5 文件上执行，且 AES 测试桩模拟 Venera 原始 CBC 输出：

如果 v1.0.5 实机仍失败，应区分记录：若失败发生在单章接口，是网络、权限或章节访问问题；若已收到 200 `application/octet-stream` 后出现新的错误，则需要保留新的 `onResponse` 堆栈。历史/收藏层的 `HistoryImageProvider`、`ComicType.sourceKey` 或 `markAsRead` Null/String 错误仍应单独处理，不能和 MOJOIN 图片解密混为一谈。

## G.19.4 v1.0.6 修复

v1.0.6 保留已经由真实站点验证的搜索接口和 `subtype=1`，新增 `normalizeSearchOption`，对白名单 `related`、`latest`、`updated`、`newest`、`oldest`、`popular`、`favorite` 做规范化。组合字符串取第一个连字符前的 key；JSON 字符串先解析；空值和未知值统一回退 `related`，避免非法排序值破坏搜索请求。
